# 编辑器集成

> 目标：在编辑器里**写指令**（补全 / 校验 / 报错）与**跑指令**（任务、终端、助手），不依赖任何 corex 专属插件。
> 多了一步却更省事的做法是 `corex create`，它替你把下面第 1 节配置好。

---

## 1. 让 YAML 有补全与校验

指令的 schema 是
[`schemas/directive.schema.json`](../../schemas/directive.schema.json)
（由 `corex-engine` 的类型生成，**请勿手改**；改类型后按 [指令 YAML](../reference/指令YAML.md) 顶部的命令重新生成）。
拿到它有**三条路**，按省事程度排：

| 做法                                 | 适合                                             | 之后会发生什么                                                                                                     |
| ------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 在该目录跑一次 `corex create <名称>` | 最省事，推荐                                     | 生成的文件头带 modeline，同目录落一份 `directive.schema.json` 副本，**编辑器下次打开就有补全、悬停文档与红波浪线** |
| `corex schema --write <路径>`        | 已有指令目录，或要把 schema 纳入版本控制         | 只落盘，编辑器侧要自己配                                                                                           |
| 编辑器设置里映射 schema              | 指令分散在多个目录，或不想让 schema 混进指令目录 | 不动指令文件本身                                                                                                   |

`schema` 子命令里那份是**编译期内嵌**的副本，与仓库里的 `schemas/directive.schema.json` 同源
（CLI 不链接 `schemars`，内嵌是唯一不引入该依赖的拿法），所以在任何工作目录、任何安装形态下答出的都是同一份。

### Modeline（文件头一行）

`corex create` 生成的文件第一行是：

```yaml
# yaml-language-server: $schema=./directive.schema.json
```

路径**相对该 YAML 文件本身**。认这一行的编辑器（VS Code + YAML 扩展、以及其它基于
`yaml-language-server` 的编辑器）会直接用它，不需要任何全局设置——这也是为什么 `corex create`
要顺手在同一目录放一份副本。

### 编辑器设置里映射

`corex schema --write` 之后，把 `yaml.schemas` 指向它。VS Code 的 YAML 扩展：

```jsonc
{
  "yaml.schemas": {
    // key 是 schema 路径，value 是要套用的文件 glob
    "./schemas/directive.schema.json": ["**/directives/*.yaml", "**/directives/*.yml"]
  }
}
```

JetBrains 系列：**Settings → Languages & Frameworks → Schemas and DTDs → JSON Schema Mappings**，
新增一条映射（Schema 文件 + 目标目录/文件模式）。其它编辑器同理——找「JSON Schema 映射」这项。

> 本仓库已经配好：`.vscode/settings.json` 里的 `yaml.schemas` 同时覆盖
> `examples/directives/*.yaml`、`examples/actions/*.yaml` 与任意 `**/directives/*.yaml`，
> 打开仓库即可用。

### 编辑时的即时校验

补全之外，`corex validate` 的判据比 schema 更严（schema 管语法与形状，validate 还管
**动作是否存在**与**权限是否覆盖**）：

```powershell
corex validate examples/directives/hello.yaml --strict  # 退出码 2 = 写法/权限问题
corex validate examples/directives/hello.yaml --watch    # 存一次盘重校一次，Ctrl+C 退出
```

`--watch` 适合放在一个终端里长跑，边写边看；它不参与 schema 的补全。

## 2. 在编辑器里跑指令

### VS Code 任务

本仓库 `.vscode/tasks.json` 已带 6 个 `cargo` 任务，`Ctrl+Shift+B`（终端 → 运行任务）即可选：

| 任务 label                   | 实际上是                                                                   |
| ---------------------------- | -------------------------------------------------------------------------- |
| `Run Hello`                  | `cargo run --bin corex -- run examples/directives/hello.yaml -i who=Corex` |
| `Schedule`                   | `… -- schedule`（列指令）                                                  |
| `Actions`                    | `… -- actions`（列动作）                                                   |
| `Validate`                   | `… -- validate examples/directives/hello.yaml --strict`                    |
| `Update Check`               | `… -- update --check`                                                      |
| `Test Workspace` / `Release` | `cargo test --workspace --locked` / `cargo build --release`                |

给自己项目加一条只跑某条指令的任务：

```jsonc
{
  "label": "corex: 跑 build-client",
  "type": "shell",
  "command": "corex",
  "args": ["run", "build-client", "-i", "profile=debug"],
  "problemMatcher": []
}
```

**要拿到退出码**（任务面板只看命令是否成功）：`corex` 的 0/1/2/3 语义见
[退出码与错误码](../reference/退出码与错误码.md)，用 `shell` 类型的任务时它原样透传。

### 集成终端

日常最省事的是直接用终端，配合补全：

```powershell
corex completions powershell | Out-String | Invoke-Expression   # 写进 $PROFILE
```

补全脚本是**回调式**的：注册脚本只把 shell 挂回 `corex`，每次按 Tab 都是本进程现算候选，
所以升级 corex 之后**不必重新生成**脚本。

常用交互入口：`corex repl`（首屏列指令与最近运行、Tab 补全）、
`corex history`（最近的执行记录，`--failed` 只看失败）、`corex doctor`（自检数据目录、配置、
守护进程、动作与指令）。

## 3. 给自动化 / 助手用的输出

corex 没有编辑器插件，但有**面向机器**的出口；任何脚本、任务或 AI 助手都靠这几样工作：

| 出口                             | 拿到什么                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| `corex paths --json`             | 本次运行的数据 / 指令目录、IPC 端点与其形态（`pipe` / `socket`）、token 文件位置        |
| `corex actions --json`           | 完整动作目录：`params`、`permissions`，以及可直接当工具入参 Schema 用的 `input_schema` |
| `corex run <名称> --json-events` | 步骤事件按 NDJSON 写到 **stdout**（最后一条固定是 `result`），进度不受干扰             |
| `corex validate <path> --strict` | 解析 + 权限覆盖校验，退出码 2 / 3 区分「写错」与「被拒」                               |

宿主**不要自己复刻 `data_dir()` 的平台规则**去拼指令路径：猜错时读的是另一棵树，而两边的
文件名往往一模一样（见 [数据目录与状态文件](../reference/数据目录与状态文件.md) §1）。
`corex paths` 把同一批事实交出来，宿主照着读就行。

三条约定：**进度写 stderr、结果写 stdout**（所以 `corex run x | jq` 与 `--json-events` 都不会被污染）；
`--json-events` 的 `kind` 与 daemon 推回的进度帧**同一套词汇**；
需要机器可读输出时用 `NO_COLOR=1` 关颜色（重定向到文件时本来就会自动关）。

### 关于 MCP

corex 现在有官方 MCP server：二进制 **`corex-mcp`**（stdio 或 Streamable HTTP），把每个
内置 Action 映射成一个 tool，另加 `corex_run_directive` 跑整条指令。Cursor / Claude Desktop /
VS Code Copilot 的配置样例与权限说明见 [MCP 接入指南](./MCP接入指南.md)。

`inputSchema`、目录 `version`、端点发现这些「喂给 MCP 宿主」的出口，就是那篇指南里
`corex-mcp` 复用的同一份 `corex_registry::catalog::document`。
