# 数据目录与状态文件

> 一处说清「corex 往磁盘上写了什么」：路径、谁写、什么时候没、能不能删。
> 随宿主分发时请显式钉住目录——见下方「为什么必须设 `COREX_DATA_DIR`」。

事实来源：[`crates/ipc/src/transport/mod.rs`](../../crates/ipc/src/transport/mod.rs)（目录解析）、
[`bins/daemon/src/main.rs`](../../bins/daemon/src/main.rs)（锁与端点）、
[`crates/engine/src/starter.rs`](../../crates/engine/src/starter.rs)（起步指令）、
[`crates/engine/src/audit.rs`](../../crates/engine/src/audit.rs) 与
[`crates/engine/src/history.rs`](../../crates/engine/src/history.rs)。

## 1. 目录在哪

解析顺序（第一个命中的就是它，**不做合并**）：

| 优先级 | 来源                                  | 备注                                                                                                      |
| ------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1      | 环境变量 **`COREX_DATA_DIR`**（非空） | 宿主与测试用它钉住目录                                                                                    |
| 2      | **可写的 exe 目录**（`corex.exe` 旁） | 便携布局；不可写就跳过                                                                                    |
| 3      | 操作系统的项目数据目录                | Windows `%APPDATA%\corex\data`；Linux `~/.local/share/corex`；macOS `~/Library/Application Support/corex` |
| 4      | 当前目录 `.corex`                     | 兜底                                                                                                      |

路径 3 由 `directories` 的 `ProjectDirs`（限定符 `dev`、应用名 `corex`）给出，
**Windows 上多一层 `\data` 后缀**，XDG 系不带。

### 为什么必须设 `COREX_DATA_DIR`

第 2 档意味着：**exe 挪个位置，数据目录就跟着挪**。随宿主分发 corex 时若不管它，
「指令、token、历史、审计落在哪」会取决于 exe 在不在可写目录——用户的旧数据会突然失联，
两台宿主也可能意外共用一份 token。

```toml
# 宿主随包携带的配置里钉不住它（数据目录在配置之前就要定下来），得用环境变量
COREX_DATA_DIR=C:\Users\Alice\AppData\Local\MyApp\corex
```

### 别把这套规则抄进宿主

宿主（编辑器、启动器、agent）常常需要知道「指令到底读的是哪个目录」。请**问**而不是**猜**：

```powershell
corex paths --json
```

```json
{
  "version": "12.1.0",
  "data_dir": "C:\\Users\\Alice\\.corex",
  "directives_dir": "C:\\Users\\Alice\\.corex\\directives",
  "endpoint": "\\\\.\\pipe\\corex",
  "kind": "pipe",
  "token_file": "C:\\Users\\Alice\\.corex\\token"
}
```

`data_dir` 走的就是上面那张表（`COREX_DATA_DIR` 优先），`directives_dir` 与
`run` / `schedule` 用的是同一处解析，`endpoint` 走连接方的发现顺序
（[`find_endpoint`](../../crates/ipc/src/transport/mod.rs)：显式配置 → `endpoint.json` → 平台默认）。

猜错的代价不只是「读不到」：Windows 上 `%APPDATA%\corex\data` 与便携布局的 `corex.exe` 旁边
都可能**恰好躺着同名指令**，于是宿主读写的是另一棵树——改了半天不生效，两边的文件名还一模一样。
`corex paths` 是唯一能直接分辨这件事的入口。

## 2. 目录内容

```text
<数据目录>/
  config/corex.toml          配置（优先于 config.toml，见 运行时配置）
  config.toml                配置（部署后常用）
  directives/                指令 YAML（按名查找时的第二站；空目录首次被触碰时会写入起步指令，见下）
  plugins/                   WASM 插件（[plugins].plugin_dir 默认值）
  token                      IPC 鉴权密钥
  endpoint.json              daemon 端点发现记录（仅服务期间存在）
  corex.lock                 单例锁（[daemon].lock_path，默认此名）
  daemon.log                 `corex daemon start` 的后台日志
  audit.jsonl                步骤级审计（只追加）
  history.jsonl              指令级执行历史（只追加）
  update-check.json          后台版本检查的状态
  cron/<id>/…                cron supervisor job 目录
  watch/<id>/…               watch supervisor job 目录
```

| 文件                | 谁写                     | 生命周期                                                                                  | 删掉会怎样                                                               |
| ------------------- | ------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `token`             | daemon（缺失时自动创建） | 长期。随机 32 字节 hex，Unix 权限 `0600`                                                  | 下次启动重建；**正在跑的 daemon 不会换**，于是旧的连不上（401）          |
| `endpoint.json`     | daemon                   | 开始服务**之前**写，退出时删。记录 `endpoint` / `kind` / `pid` / `token_file` / `version` | 连接方退回平台默认端点。强杀 daemon 会留下**残留**，它不等于 daemon 在跑 |
| `corex.lock`        | daemon                   | 进程存活期间**持有**（单例互斥）                                                          | —                                                                        |
| `daemon.log`        | `corex daemon start`     | 追加，不轮转                                                                              | 丢日志                                                                   |
| `audit.jsonl`       | CLI / daemon             | 只追加                                                                                    | 丢审计（合规场景**不可**删，见 [合规说明](../ops/合规说明.md)）          |
| `history.jsonl`     | CLI / daemon             | 只追加；`[history].enabled = false` 可关                                                  | `corex history` 变空                                                     |
| `update-check.json` | CLI 后台检查             | 记上次检查时间与已知版本                                                                  | 下次启动重新检查一遍                                                     |

### 起步指令

数据目录里的 `directives/` **一条指令都没有**时，第一个触碰它的 corex 进程会写入几条通用
起步指令（`system-info` / `dir-tree` / `dir-backup` / `text-fingerprint` / `reminder`），
让宿主第一次打开不是一张白纸。内容和写入逻辑见
[`crates/engine/assets/starters/`](../../crates/engine/assets/starters/) 与
[`crates/engine/src/starter.rs`](../../crates/engine/src/starter.rs)。

| 问题                     | 答案                                                                        |
| ------------------------ | --------------------------------------------------------------------------- |
| 什么时候写               | 目录里**一个 `.yaml` / `.yml` 都没有**时；只看一层                          |
| 谁会写                   | CLI（`paths` / `doctor` / `run` / `schedule` / …，凡是走默认指令目录的命令）、daemon 启动、MCP |
| 会覆盖吗                 | 不会。目录里已有指令就一条都不写，更不改动已有文件；`README.md`、`*.bak` 之类的杂物不算「已有指令」 |
| 删掉会回来吗             | 删单条不补；把目录腾空，下次启动再全量写一遍                                |
| `--dir` / `--directives` | 指定的目录一律**不**播种——那是你自己挑的目录                               |
| 不想要怎么办             | 直接删。没有开关要关                                                        |

起步指令是普通指令：可改、可删、可与 `examples/directives/` 里的示例并存（名字刻意不重合）。
企业打包时若不想让它出现，往 `directives/` 里预置**任意一个** `.yaml` 即可（哪怕是个占位文件）。

### `endpoint.json` 的读法

连接方顺序是 **显式配置 → 该文件 → 平台默认**；监听方（daemon）**从不读**它——崩溃残留的记录会把
新起的 daemon 带到上一个进程的端点上。`pid` 仅供排错，**不做存活性判断**（pid 会被复用）。
判断「daemon 在不在跑」的办法是发一条 `ping`。字段与示例见
[IPC 协议 § 端点发现文件](./IPC协议.md#端点发现文件)。

### supervisor job 目录

`corex cron` / `corex watch` 每个 job 一个目录（见 [架构 § 数据目录布局](./架构.md#数据目录布局)）：

| 路径                         | 内容                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| `<kind>/<id>/meta.json`      | 指令名/路径、pid、表达式、`supervisor_exe`、`started_at_ms` |
| `<kind>/<id>/supervisor.log` | supervisor 自己的日志                                       |
| `<kind>/<id>/control.cmd`    | 待消费的 control 消息（写入后由 supervisor 轮询删除）       |

`<id>` 就是**指令名**——所以 `ps` / `send` / `stop` / `attach` 都用指令名，不用 pid。
存活判定要求 pid 在、exe 路径匹配、启动时间在容差内（防 PID 复用）；缺字段的旧 `meta.json`
视为已失效，可由 `prune_stale` 清理。

## 3. 并发与多宿主

| 事项         | 规则                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------- |
| 单例锁       | **每个数据目录一份**（`corex.lock`）；同一数据目录起两个 daemon 会被锁挡住                         |
| Windows 端点 | 默认恒为 `\\.\pipe\corex`，**不随数据目录变** → 两个各带 `COREX_DATA_DIR` 的宿主仍会抢同一个管道名 |
| Unix 端点    | 默认 `<数据目录>/corex.sock`，数据目录不同就天然隔离                                               |

所以 Windows 上要并存两个宿主，除了各自的 `COREX_DATA_DIR`，还要**各自给一个 `socket_path`**
（如 `\\.\pipe\my-app-corex`）。晚起的 daemon 会因管道被占而**响亮地失败**：进程直接退出、
不留端点记录，报错里指向 `socket_path`。

## 4. 排查用的只读入口

| 想知道                   | 命令                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| 数据目录到底在哪         | `corex paths`（数据 / 指令目录与端点，`--json` 给机器读）；`corex doctor`（顺带自检一遍）  |
| 端点与 token 对不对      | `corex daemon status`                                                                      |
| 最近跑过什么、为什么失败 | `corex history` / `corex history --failed`                                                 |
| 卡片上的「上次运行」     | IPC `list_runs` / `list_directives` 条目的 `last_run`（同一份账本，只读）                  |
| 生效的是哪份配置         | `corex validate`（不给路径时检查配置）                                                     |
