# 退出码与错误码（v10）

> 面向脚本、CI 与宿主：这是 corex 对外的**两个稳定契约**——进程退出码，以及错误分类字符串 `kind()`。

事实来源：[`bins/cli/src/exit.rs`](../../bins/cli/src/exit.rs)（退出码表）、
[`crates/core/src/error.rs`](../../crates/core/src/error.rs)（`kind()`）。

- **进程退出码**：`corex` CLI 给 shell / CI / 任务计划的，只有 4 个值。
- **`kind()`**：机器可读的错误分类，写进 `audit.jsonl`、`history.jsonl`，也是退出码判定的输入。

两者不是一回事：同一种失败在两条通道上的名字不同，混用会写出脆的脚本。

---

## 1. 退出码

| 码    | 名称      | 含义                                                                               |
| ----- | --------- | ---------------------------------------------------------------------------------- |
| **0** | `Success` | 命令按要求完成                                                                     |
| **1** | `Failure` | 命令运行了但失败                                                                   |
| **2** | `Usage`   | 调用方式或输入不对：参数写错、指令/动作未知、YAML 解析失败、参数非法、**配置损坏** |
| **3** | `Denied`  | 权限或策略门禁拒绝了该动作（含被 `plugins.disabled*` 关掉的动作）                  |

### 判定规则

`ExitStatus::read` 沿着 `anyhow` 的 cause 链找**第一个**带类型的 `ActionError` / `EngineError`，
用它查表；外层的 `anyhow` 上下文只加说明文字，不参与分桶。

CLI 自己 `bail!` 出来的错误**不带类型**，因此一律落进 `Failure`(1)——不去猜它属于另外三桶中的哪一桶。

### `not_found` 为什么有两张表

同一个字符串在两侧含义相反，所以**不能**按 `kind()` 字符串直接选桶：

| 场景                             | `kind()`    | 退出码 | 为什么                              |
| -------------------------------- | ----------- | ------ | ----------------------------------- |
| `EngineError::DirectiveNotFound` | `not_found` | **2**  | 用户点名的指令不存在——写法问题      |
| `ActionError::NotFound`          | `not_found` | **1**  | 动作要找的文件/窗口没了——运行期问题 |

引擎的 `kind()` 对 `StepFailed` / `Action` 会**委派**给内层动作错误，于是这个双关会被抹平。
`ExitStatus::read` 因此跳过 `kind()`，直接按**类型**取出内层错误再查动作表。

### daemon 不参与这套

`corex-daemon` 启动失败（含配置无效）**一律退 1**。它是由监督进程拉起的服务，退出码不是脚本契约；
分类表只存在于 `bins/cli`。宿主判断 daemon 状态请发 `ping`，不要看退出码。

### `corex run --remote` 的折回

经 IPC 跑时，daemon 已经把错误压成了字符串，CLI 只能按码分桶。折回表（见
[`bins/cli/src/run.rs`](../../bins/cli/src/run.rs) 的 `from_rpc`）：

| IPC `error.code`     | 折回成                          | 退出码 |
| -------------------- | ------------------------------- | ------ |
| `403`                | `ActionError::PermissionDenied` | **3**  |
| `400` / `404`        | `EngineError::Usage`            | **2**  |
| `401` / `500` / 其它 | 通用失败                        | **1**  |

`401`（token 不对）刻意**不**算用法错误：环境没配好不是命令写错了。
文案一律原样透传，不再叠「指令未找到: 动作未注册: …」这类前缀。

效果是：`corex run hello --remote` 与本地 `corex run hello` 对同一种失败给出**同一个数字**。

## 2. `kind()` 分类

### `ActionError::kind()` — 单次动作

| `kind()`            | 触发                                        |
| ------------------- | ------------------------------------------- |
| `permission_denied` | 权限 / 策略拒绝 → 退出码 3                  |
| `timeout`           | 超时                                        |
| `invalid_params`    | 缺参或参数非法 → 退出码 2                   |
| `not_found`         | 目标不存在（运行期）                        |
| `disabled`          | 动作被禁用（`plugins.disabled*`）→ 退出码 3 |
| `io`                | 文件系统错误                                |
| `execution`         | 其余执行失败                                |
| `ui_*`（动态）      | 见下节；没有细化码时回落到 `execution`      |

`MissingParam` 与 `InvalidParams` 共用 `invalid_params`；`ExecutionFailed` 与 `Other` 共用
`execution`（除非消息里带了 UI 码）。

### `EngineError::kind()` — 指令读取与流水线

| `kind()`                | 触发                                           | 退出码   |
| ----------------------- | ---------------------------------------------- | -------- |
| `not_registered`        | 动作未注册                                     | 2        |
| `not_found`             | 指令不存在（**仅限这条路径**）                 | 2        |
| `parse`                 | YAML 解析失败                                  | 2        |
| `config`                | 配置错误                                       | 2        |
| `usage`                 | 调用方式错误                                   | 2        |
| `resolve`               | 变量未定义 / 解析失败                          | 1        |
| `control_flow`          | 条件求值失败、控制流错误（可能依赖运行期数据） | 1        |
| `io`                    | 文件系统错误                                   | 1        |
| `execution`             | 其余（含 `Other`）                             | 1        |
| `StepFailed` / `Action` | **委派**给内层 `ActionError::kind()`           | 按动作表 |

`StepFailed` / `Action` 是包装：它们没有自己的分类，答案取自内层错误。

### 动态的 `ui_*` 码

`ActionError::ExecutionFailed` / `Other` 的消息里带方括号标签（如 `[ui_login_pending]`）时，
`kind()` 返回**该标签本身**，否则回落 `execution`。当前内置的码：

| 码                      | 场景                              |
| ----------------------- | --------------------------------- |
| `ui_scope_required`     | 需要 `scope` 才能定位元素         |
| `ui_desktop_not_found`  | 找不到桌面 Shell 窗口             |
| `ui_selector_not_found` | 选择器没有命中任何元素            |
| `ui_wrong_window`       | 命中的元素属于别的窗口            |
| `ui_not_clickable`      | 元素存在但不可点击                |
| `ui_sync_timeout`       | 等待元素状态同步超时              |
| `ui_login_pending`      | 检测到仍在登录/未就绪（OCR 场景） |

选择器细节另有**脱敏**的 `selector_hint`，走 `[selector_hint=...]` 标签，由
`ActionError::selector_hint()` 取出。脱敏规则见 [威胁模型](../ops/威胁模型.md)。

> 这些码是**加法式**的：宿主可以按前缀 `ui_` 归组，但不要假设集合封闭。

## 3. 权限拒绝的特殊地位

`permission_denied` 与 `disabled` 是唯一能把退出码抬到 **3** 的一类，且行为上被特殊对待：

- **`on_error: continue` / `skip` 吞不掉它**——`PermissionDenied` 始终中止该步骤及整条流水线，
  否则门禁就能被一条 `continue` 绕过（见 [指令 YAML](./指令YAML.md)）。
- **并行分支同时失败时，引擎优先保留权限拒绝错误**。
- 审计里它体现为 `denied: true`，而不是靠 `error_kind` 字符串判（见 [审计日志](../guide/运行时配置.md#审计日志)）。

判定口径：`ActionError::is_permission_denied()` / `EngineError::is_permission_denied()`，
对包装类型会问内层。**不要**用 `error_kind == "permission_denied"` 替代它——那是字符串匹配。

## 4. 怎么写基于退出码的脚本

```powershell
corex run deploy
switch ($LASTEXITCODE) {
  0 { 'ok' }
  2 { '参数或指令写错了，别重试' }
  3 { '被策略拒绝：检查 permissions / disabled_actions' }
  default { '跑失败了：看 corex history --failed' }
}
```

```bash
if ! corex validate d.yaml --strict; then
  echo "校验没过（多半是退出码 2）" >&2
fi
```

要**机器可读的失败原因**时，别去解析 stderr 文案——读 `history.jsonl` 的 `error`，或让宿主走 IPC
拿 `error.code` / `message`。
