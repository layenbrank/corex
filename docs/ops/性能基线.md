# 体积与冷启动基线

这份文档记录**产物体积**与 `corex --version` 的**进程冷启动耗时**，以及复测方法和自动门禁。

它存在的理由：这两项最容易因为「顺手加一个依赖」而退化，而 `fmt`、`clippy`、单元测试**都不会因此变红**——
一个多出来的重依赖可以让启动路径变长好几倍，测试仍然全绿。

## 实测值

采集于 Windows x86_64，本地 rustc 1.95.0（CI 用 1.98.0）。体积是文件字节数，冷启动每次都起**新进程**、连跑 10 次。

| 产物              | 构建    | 体积                      |
| ----------------- | ------- | ------------------------- |
| `corex.exe`       | release | 12,387,328 字节（11.81 MB） |
| `corex-daemon.exe`| release | 22,871,552 字节（21.81 MB） |
| `corex.exe`       | debug   | 46,156,800 字节（44.02 MB） |
| `corex-daemon.exe`| debug   | 78,878,208 字节（75.22 MB） |

| 构建    | 中位数   | 最大     |
| ------- | -------- | -------- |
| release | 62.7 ms  | 70.5 ms  |
| debug   | 43.7 ms  | 51.7 ms  |

这些是同一台机器、同一天的实测快照。重复测量时 debug 中位数在 **41–52 ms** 之间波动（机器噪声），体积也会随内部重构有 KiB 级漂移——**门禁和下面的排查清单都不依赖这些绝对值**。

两点需要解释，否则数字会被误读：

- **release 不一定比 debug 启动快**。`--version` 这种路径的主要成本是加载可执行文件与动态初始化，与优化等级关系不大；
  几十毫秒级别里，两个构建的差异落在噪声范围内。冷启动要抓的是**结构性变化**，不是这里的小数点。
- **daemon 大约是 CLI 的两倍**，这是预期的：它是唯一启用 `wasm` 特性、因而链接 wasmtime / cranelift 的产物。
  CLI 依赖树里出现 `wasmtime` 就说明 Phase 1 的 feature 隔离被破坏了（见「体积突变时先看哪里」）。

本地 release 构建耗时约 6 分 18 秒（`lto = true` + `codegen-units = 1`），0 warning。

## 自动门禁

`.github/workflows/build-and-test.yml` 的 `build-and-test` 任务末尾有一个 `Cold start and binary size` 步骤：

- 连跑 10 次 `target/debug/corex.exe --version`，取排序后的中间位（10 次即第 6 个）作为中位数；
- 打印 `corex.exe` / `corex-daemon.exe` 的体积；
- **中位数超过 2000 ms 即失败**。

三个刻意的选择：

1. **跑 debug 而不是 release**：release 在 CI 上要几分钟，而这一步的目的是抓结构性回归，debug 足够灵敏。
   release 体积由 `publish-release.yml` 在打包时打印（`OK <name> (<x.xx> MB)`），发布流程本来就会看。
2. **上限留了两个数量级余量**（实测 debug 中位数 41.6 ms）：CI 机器的噪声远大于本地，卡到 100 ms 级只会变成随机失败。
   2000 ms 抓的是「启动时多做了几百毫秒的工作」这类问题，例如启动时扫描插件目录、或把 wasmtime 拉进 CLI 的启动路径。
3. **不引入 `criterion` 或基准测试框架**：那会给一个刚做过瘦身（摘掉 wasmtime、pdfium 死重）的仓库再加一棵基准依赖树，
   而当前**并没有已知的性能问题需要微基准去定位**。缺的是「不许悄悄退化」的守门人，由上一步承担。
   真需要微基准时再单独加，并让它跑在独立任务里。

## 本地复测

release（要同时量 daemon 才需要 `-p corex-daemon`；只关心 CLI 时去掉它即可，能省掉 wasmtime / cranelift 的编译）：

```powershell
cargo build --release -p corex -p corex-daemon --locked
$rel = Join-Path $env:CARGO_TARGET_DIR 'release'
Get-ChildItem "$rel\corex.exe", "$rel\corex-daemon.exe" |
  ForEach-Object { "{0} = {1:N0} bytes = {2:N2} MB" -f $_.Name, $_.Length, ($_.Length / 1MB) }
$t = 1..10 | ForEach-Object { (Measure-Command { & "$rel\corex.exe" --version | Out-Null }).TotalMilliseconds }
$t | Sort-Object | Select-Object -Skip 4 -First 2 | Measure-Object -Average
```

更快的 debug 口径（与 CI 一致）：

```powershell
cargo build --workspace --locked
$dbg = Join-Path $env:CARGO_TARGET_DIR 'debug'
$t = 1..10 | ForEach-Object { (Measure-Command { & "$dbg\corex.exe" --version | Out-Null }).TotalMilliseconds }
$t | Sort-Object | Select-Object -Skip 4 -First 2 | Measure-Object -Average
```

> `CARGO_TARGET_DIR` 若在本地被设置过，产物**不在**仓库的 `target/` 下。CI 没有这个变量，所以 workflow 里写的是 `target/debug/corex.exe`。

## 体积突变时先看哪里

启动变慢或体积变大时，按顺序排除：

```powershell
# 1. 依赖树规模。本机当前 786 行（行数随平台/feature 变化，只跟同一命令的历史值比）。
cargo tree -p corex | Measure-Object -Line

# 2. CLI 不该链接 wasm 运行时 —— 两条都应输出为空
cargo tree -p corex | Select-String wasmtime
cargo tree -p corex | Select-String cranelift

# 3. schema 是可选特性，默认构建不该带上生成器
cargo tree -p corex | Select-String schemars
```

第 2、3 条之所以是「应该为空」：CLI 在进程内执行指令、从不加载插件，`wasm` 只由 `corex-daemon` 启用；
`schemars` 只在 `corex-engine` 的 `schema` 特性下存在。它们出现在 CLI 的依赖树里，就是 feature 隔离被破坏。
