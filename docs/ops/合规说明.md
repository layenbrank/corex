# 合规说明（corex 指令）

## 范围

本文覆盖使用 corex 指令（`ui.*`、`capture.*`、`shell.run`）做**经授权的桌面自动化**。
**不是**法律意见。

## 原则

1. **先授权** — 只自动化操作者有权控制的应用与账号。未经书面政策与法务审查，勿用 corex 做隐蔽的员工监控。
2. **最小权限** — 启用 `strict_permissions`、设置 `filesystem_roots`，并在 `disabled_actions` 中列出高风险 ID（见 [enterprise-deploy.md](企业部署.md)）。
3. **禁止静默同步到生产** — `examples/` 下的示例指令（含微信 / IM 配方）**不得**由默认安装程序或企业 MDM 包复制进 daemon 的 directives 目录。
4. **第三方服务条款** — 自动化即时通讯（微信、Slack 等）可能违反厂商 ToS。相关配方视为**实验且脆弱**；投产前须获批准。
5. **PII / 屏幕数据** — 截图与 OCR 可能捕获机密。历史/审计中不得保留 OCR 全文（引擎脱敏）。限制谁能开启 `permissions.capture` 与 `permissions.ui`。

## 推荐控制项

| 控制 | 设置 |
|------|------|
| 拒绝 unrestricted（运行时） | `[runtime].strict_permissions = true` |
| 路径沙箱 | `[runtime].filesystem_roots = [...]`（含 `exec.run` script 与启动 `cwd`） |
| 默认禁用 UI/OCR/shell/keyring/scan | `[plugins].disabled_actions`（[enterprise.toml](../../config/enterprise.toml)） |
| 静态覆盖校验 | `corex validate --strict path.yaml` |
| 便于 SIEM 的日志 | `[logging].json = true` + `audit.jsonl` |

`strict_permissions` 只拒绝**完全未声明**权限标志的指令。
`validate --strict` 还会遍历每个步骤，要求声明的类别覆盖对应 Action。

## 人在回路检查点

部分 UI 自动化配方（例如 [`examples/directives/wechat-send-message.yaml`](../../examples/directives/wechat-send-message.yaml) 中的微信 4.x 登录）在 PC 端脚本点击按钮后，需要**操作者在第二台设备上操作**（例如点 **进入微信**）。corex **不会**自动化手机端；只等待 PC UI 变化（`ui.element.wait`，`state: absent`）。

| 检查点 | 操作者动作 | PC 侧行为 | 失败信号 |
|--------|------------|-----------|----------|
| 手机登录确认 | 在手机上点 **同意/登录** | 最长等待 `login_timeout_ms` | 审计中的 `[ui_login_pending]`（`error_code`） |
| 中止 / 超时 | 无 | 流水线失败关闭；不部分发送 | 审计 `ui_phase=login`、`selector_hint` |

生产环境启用 `permissions.ui` 前：

1. 记录谁可以运行依赖登录的指令。
2. 按操作者节奏设置合适的 `login_timeout_ms`。
3. 将 `examples/` 中的指令 YAML 同步到 `%LOCALAPPDATA%\corex\directives\`，使 `default` 输入与登录分支与已签名配方版本一致。
4. 审查 `audit.jsonl` 中的 `ui_login_pending`（`error_code` / `error_kind`）与 `denied`，而非笼统的执行错误。
