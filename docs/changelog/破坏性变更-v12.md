# 破坏性变更 — Corex v12

v12 把「宿主怎么读写指令」这件事收进 daemon：路径、YAML 解析、写盘格式全在 corex 一侧，
宿主只拿模型改模型。副作用是 `list_directives` 的回包换了形状，而指令 YAML 多了一个
**有取值约束**的 `bucket`。

---

## 1. `list_directives` 回的是条目，不是名字

v11 回的是裸名字数组：

```json
["build-intern", "hello"]
```

v12 回 `{name, path, bucket, summary}`。名字不够用：宿主得知道指令**在哪个文件**（才能显示、
才能交给外部编辑器），也得知道分类与描述、步骤数（才能在侧栏归类、画出卡片）；让宿主自己拼路径
意味着它要复刻一遍 `data_dir()` 的平台规则，猜错时读的是另一棵树，而两边的文件名往往一模一样。

```json
[
  {
    "name": "build-intern",
    "path": "C:\\Users\\Alice\\.corex\\directives\\build-intern.yaml",
    "bucket": null,
    "summary": { "description": "", "step_count": 3, "input_count": 1, "trigger_count": 0 },
    "last_run": {
      "started_at_ms": 1763818203123, "ended_at_ms": 1763818204444, "ok": false,
      "error": "execution: 渲染失败: 变量 `missing` 未定义", "duration_ms": 1321,
      "run_count": 4, "failed_count": 1
    }
  }
]
```

`summary` 是**解析成功**才有的：文件坏了（分类与元信息都读不出来）它是 `null`，条目照样
列出来——用户正是要靠这份列表在编辑器里打开坏文件去修。列目录时那次解析顺手把
`description` / `step_count` / `input_count` / `trigger_count` 一起给了，宿主不必为了画
一张卡片把每个文件再读一遍。

条目上还有一个 `last_run`（**没跑过、或 `[history]` 关掉时整个字段不出现**）：最近一次
执行的 `ok` / `duration_ms` / `error`，外加窗口内的 `run_count` / `failed_count`。这份账本
一直是引擎在跑完的当口写的（就是 `corex history` 读的那份），宿主不该再存一份「上次运行
时间」——换台机器、清过数据目录就会与它各说各话。

同时新增三条请求：两条构成完整的读写闭环，一条把执行历史开成**只读**出口：

| 请求             | 字段                                             | 回什么                                   |
| ---------------- | ------------------------------------------------ | ---------------------------------------- |
| `read_directive` | `name`，`dir?`                                   | `{name, path, text, definition}`         |
| `save_directive` | `name`，`definition`，`dir?`                     | 同上，`text` 是**刚写下去**的那份        |
| `list_runs`      | `name?`，`limit?`                                | `{is_history_enabled, entries}`，新 → 旧 |

`definition` 就是 `corex_engine::Directive` 的 JSON 形状：宿主拿 `text` 展示、拿
`definition` 编辑，改完原样交回 `save_directive`。写盘格式（键序、哪些默认值该省）只有
引擎一份，宿主不必、也不该自己拼 YAML。`list_runs` 读的也是引擎那一份，`is_history_enabled`
让它能分清「历史没开」与「一条都没跑过」。

### 要做什么

- 读 `list_directives` 的代码改成读对象字段（`.name` / `.path` / `.bucket`），要画卡片就读 `.summary`（可能为 `null`）。
- 自己实现过「找指令文件 + 解析 YAML + 拼 YAML 保存」的宿主，把这三件事换成上表三条请求。
- 卡片上的「上次执行时间 / 上次成功没 / 跑了几次」直接读 `last_run`；宿主库里再存一份必然与
  引擎的账本对不上，清过数据目录就会只剩一份骗人的时间。
- 路径拿不准时先问 `corex paths --json`（见第 4 节），不要复刻平台规则。

### 顺带修正的错误码

`run_directive` / `read_directive` 遇到不存在的指令原本回 **500**（`bail!` 落到通用失败），
现在回 **404**；名字不是裸名（含 `..`、分隔符或绝对路径）回 **400**，`dir` 逃出指令根回 **403**。
「错的是调用方点的名字」不该报成服务端内部错误。

## 2. `bucket` 有取值约束

指令 YAML 顶层新增 `bucket`（可选），取值与 `corex actions` 的动作分类**同一套**：
`system` / `network` / `data` / `ui` / `logic` / `plugin`。它只是给人分组用的标签，
不影响执行。

```yaml
name: build-intern
bucket: logic
```

**破坏面**：以前写在顶层、corex 不认识的键一律被忽略；`bucket` 是第一个会**当解析错误拒掉**
的未知取值。写别的值（例如 `bucket: intern`）现在会让整条指令解析失败——与其悄悄丢掉
分类让人以为是编辑器坏了，不如当场说清。

顺带说明：分类是**动作**的概念，不是「这条指令属于哪个项目」的标签。给指令分组用目录
（`directives/<子目录>/`），别拿名称后缀（`build-intern.yaml`）当分类。

---

## 3. `Directive` 的序列化不再写出空默认值

`corex_engine::Directive` 及步骤类型的 `serde` 属性补上了 `skip_serializing_if`：空
`description`、空 `inputs` / `variables` / `triggers`、未声明的 `permissions`、默认的
`on_error`、`params: null` 都不再出现在输出里（**反序列化行为不变**，缺字段仍是默认值）。

新增 `Directive::to_yaml_str()`：把模型写成 YAML 文本。它产出的是**规范化文档**，注释与
键序不会保留——`save_directive` 用的就是它。

---

## 4. `corex paths`：目录与端点只有一处事实

新增 `corex paths [--json]`，打印本次运行真正使用的位置：

```json
{
  "version": "12.0.0",
  "data_dir": "C:\\Users\\Alice\\.corex",
  "directives_dir": "C:\\Users\\Alice\\.corex\\directives",
  "endpoint": "\\\\.\\pipe\\corex",
  "kind": "pipe",
  "token_file": "C:\\Users\\Alice\\.corex\\token"
}
```

`data_dir` 走的就是 [数据目录与状态文件](../reference/数据目录与状态文件.md) §1 那张表
（`COREX_DATA_DIR` → 可写的 exe 目录 → 系统数据目录 → `.corex`），`endpoint` 走连接方的
发现顺序。宿主**不要**自己复刻这些规则：可写的 exe 目录这一条就足以让便携安装与系统安装
落在两棵树上，而 `%LOCALAPPDATA%` 之类「看起来对」的猜法正好会读到过期的旧副本。

## 5. 两道门搬进引擎，拒绝信息的措辞跟着变

「动作是否注册」「运行时权限够不够」这两道门原本只长在 CLI 里
（`bins/cli/src/steps.rs` 的 `require_registered` / `require_allowed`），daemon 侧没有——
于是 `save_directive` 能把一条跑不起来的指令写进盘。现在它们是
`corex_engine::validate_registered` / `validate_allowed`，引擎、CLI、daemon 共用一条遍历
（`validate_permissions` 也改用同一条，行为不变），CLI 里那两份实现删除。

**破坏面**落在直接调过 CLI 私有函数的人（本仓内只有 CLI 自己）与**读拒绝文本**的脚本：
`validate_allowed` 不再叠一层「权限不足」前缀，改为点名动作与缺的类别。

```text
v11: 权限不足: shell: 权限不足: 指令未声明权限 shell 以执行 shell.run
v12: 权限不足: shell: shell.run 缺少权限 shell
```

`corex run --dry-run` 与 `corex validate` 的判定与退出码（2 = 写错、3 = 被拒）不变。

## 6. `template.render` 的参数不再被预解析

v11 里动作参数在交给动作**之前**统一过一遍[占位符解析器](指令YAML.md#占位符解析器)，
而 `template.render` 自己又用 MiniJinja 渲染同一个字符串——于是模板在到达 Jinja 前
就被替换成字面量：

```yaml
template: '{{ input.q | urlencode }}'
```

v11 把 `input.q | urlencode` 整个当成变量名去查，报 `变量未定义: input.q | urlencode`。
过滤器和 `{% %}` 从来没生效过，只能写裸 `{{x}}`。

v12 给 `Action` 加了 `is_raw_params()`：返回 `true` 的动作拿到的是**原始参数**。
目前只有 `template.render` 置位（它是唯一自己解释模板语法的动作），其余动作的解析行为不变。
模板上下文与占位符解析器**同源**（裸名先变量后输入），并补齐 `input` / `variables` / `var` /
`step` / `steps` / `env` / `directive_input`，过滤器和 `{% %}` 现在真的可用。

同一处还改了四件事：

- **未定义变量直接报错**（`UndefinedBehavior::Strict`）：以前拼错变量会静默渲染成空串，
  现在报 `undefined value`。代价是错误文案不再带变量名（旧的是 `变量未定义: xxx`），
  因此渲染失败的文案会拼上**出错那行的模板原文**：
  `渲染失败: undefined value (in tpl:1) | 模板: {{ no_such_var }}`。要给默认值写
  `{{ x | default('y') }}`，判存在写 `{% if x is defined %}`。`default` 默认只兜未定义，
  而 `on_error: continue` 写进去的是 `null`（已定义），要兜住得写 `{{ x | default('y', true) }}`。
- **开启 MiniJinja 的 `urlencode` 特性**：`| urlencode` 此前是 `unknown filter`。它与
  `codec.url.encode` 的转义集略有差别（前者不转义 `/`），要精确控制编码用 `codec.url.encode`。
- **对象 / 数组的混插值渲染成 JSON 形状**：`{{ m }}` 混在别的文本里时，旧的是 `Value::Display`
  的 `{k: v}`，现在是 `{"path": "out.txt", "removed": 1}` / `["a", "b"]`（分隔符是 MiniJinja
  自己的 `", "`）。二进制仍然是 `<N bytes>`，与旧的一致；`null` 渲染成 MiniJinja 的 `None`。
- **`{{ 变量 }}` 的取值规则不变**：裸名仍是先变量后输入，`input` / `variables` / `var` /
  `step` / `steps` / `env` / `directive_input` 都补齐了，`hello.yaml`、`resolver-demo.yaml`
  这类老指令的输出一字未变。

### 要做什么

- 依赖「参数先被解析、模板拿到替换后的值」这种绕法写指令的，直接写正常模板即可。
- 想新增自己解释模板语法的动作，实现 `Action::is_raw_params() -> true`，并自己补齐上下文。

## 7. 子进程的输出改成帧，`--json-events` 的 stdout 因此干净了

v11 里 `shell.run` / `exec.run` 把子进程的 stdout / stderr 分块**直接写自己的进程流**
（`process_launch` 的 `echo`）。本地跑没问题——那正是调用方的终端；**经 daemon 跑就等于丢失**：
字节流向了 daemon 的控制台，客户端（Studio 的运行面板、`corex run --remote`）一个字节也拿不到，
表现是「日志里只有步骤，没有命令输出」。`corex run --json-events` 更糟：子进程原文混进
NDJSON，破坏机器可读。

v12 起这些文本走**上报口**，与进度同一套通路：本地执行由 CLI 的渲染器原样落到原流，远程执行
变成 `step_output` 帧（见 [IPC 协议](../reference/IPC协议.md#进度帧-stream-true)）。

- 新增 `corex_core::Stream`（`stdout` / `stderr`）与 `Observer::output(&self, at, stream, text)`；
  `Reporter::output(stream, text)` 是子进程泵里唯一带得进的上报方式。
- `ProgressEvent` / 协议新增 `{"kind":"step_output","step":…,"action":…,"stream":…,"text":…}` 帧。
- 没有上报口时（`--quiet`、或嵌入宿主压根没挂口子）行为与从前**逐字节一致**：仍旧直写自己的流。

### 要做什么

- 按 NDJSON 消费 `--json-events` 的：现在 stdout 上**只有**帧 JSON，子进程原文包在
  `step_output.text` 里。这是好事，但按行解析的老脚本会看到字段而非裸文本。
- 解析帧时**不要假设 `text` 是一行**：它是读缓冲的切片，可能半行断开，按到达顺序拼接才是完整
  输出。要完整读一次，用终帧里动作的 `stdout` / `stderr` 字段。
- 只需要「有没有输出」的宿主可以忽略这个 `kind`，其余帧与终帧的形状没变。

## 8. `max_jobs` 默认不再串行，排队改由心跳说话

v11 的 `[daemon] max_jobs` 默认 `1`：一条指令跑着的时候，别的执行请求**在队列里等**，而排队
期间**一帧都不发**。对客户端来说，「排在一小时长的队列里」与「daemon 卡死了」完全一样，于是
长排队会把宿主的请求时限撞穿——超时被报成失败，请求其实还在队列里，之后照样执行，副作用真的
发生了。v12 两处一起改：

- **默认 `max_jobs = 4`**：宿主的「多任务并跑」（构建、拷贝、压缩之类互不相干的重活）本就
  互不干扰，串起来只会让后面几条一直排队。要保住「两条指令不会同时驱鼠标键盘」这条 UI 自动化
  前提的宿主，**显式写 `max_jobs = 1`**。
- **新增 `heartbeat` 帧**：`{"kind":"heartbeat","is_queued":true,"waited_ms":4200}`，从请求到达
  到它跑完每两秒一帧，`is_queued` 区分「在队列里等」与「已经在跑」（只发给 `stream: true` 的请求）。

### 要做什么

- 判请求死没死，用**静止期**而不是总时长：收到任何帧（含心跳）就重置计时。把 60s 总时长套在
  「执行一条要两分钟的指令」上，本来也会误报——心跳只是让它更明显。
- 分不清 `kind` 的客户端可以忽略心跳：它不属于任何步骤，CLI 的 `Steps` / `Events` 渲染器
  也不重放它。
- 依赖「daemon 串行执行」的部署（尤其是发 `ui.*` / `capture.*` 的）必须在配置里写回
  `max_jobs = 1`；不写就会并行，两条指令同时驱鼠标键盘会互相踩。
