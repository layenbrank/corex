# 破坏性变更 — Corex v13

v13 只做一件事：把**指令从哪里来**收成一处。

v12 及以前，指令的真相是磁盘上的 YAML 文件，于是每个入口都长出了一套自己的「指令根」：

| 入口   | 它看的指令根                                                                       |
| ------ | ---------------------------------------------------------------------------------- |
| CLI    | 当前目录的文件 → `<数据目录>/directives/*.yaml`（只看一层）→ 仓库 `examples/directives/` |
| daemon | `<数据目录>/directives/*.yaml`（只看一层），`--directives` 可以另指一处              |
| MCP    | `--directives` 指定的目录                                                           |
| 宿主   | 自己复刻一遍上面的路径规则；找不到用户装的那份时，还可能退回自带的私有目录           |

四套规则下，「同一条指令在哪」本身就说不清；而执行日志在**另一个文件**里
（`history.jsonl`），宿主想让卡片显示「上次执行时间」就只能在库里再存一份——换台机器、
清过数据目录，两份就各说各话。

v13 起：**指令与执行日志都在 `<数据目录>/corex.db`**（SQLite，对齐 `i-thinking.db` 命名），YAML 退到它本来该待的
位置——导入 / 导出 / 编辑往返。

---

## 1. 指令库：唯一真相源

```text
<数据目录>/corex.db
  directives   name(PK) · folder · source · definitionJson · visible · createdAt · updatedAt
  runs         directive · startedAt · endedAt · ok · error · duration · recordedAt
```

- **键是名字，不是路径。** `name` 由库持有，`definitionJson` 里的 `name` 永远被它覆盖——
  v12 的「文件主干与 YAML 里的 `name` 不一致，于是卡片一直显示未运行」这类毛病不会再出现。
- **模型整体存 JSON**，不拆列：拆分会让库变成第二份 schema，改一次 `Directive` 要动两处。
- **`folder` / `source` / 两个时间戳**是库自己的元信息：导入目录时，相对子目录成为 `folder`；
  `source` 记原文件路径，便于日后对账；`updatedAt` 就是宿主显示「什么时候改的」。
- **`runs` 与指令同库**：`[history]` 那一份账本（`corex history`、IPC `list_runs`、卡片上的
  `last_run`）现在读的是这张表。`(directive, startedAt, endedAt)` 上有一条唯一索引，
  所以重复写入不会重复计数，旧账本也能反复导入。
- **列名 camelCase**（对齐 i-thinking.db）：不用 `created_at_ms` / `definition_json` 这类 snake_case。
- **并发**：WAL + 5s busy timeout。CLI 与 daemon 同时写（用户在终端跑 `corex run`，Studio
  也在跑）时后到的一方等前者的事务结束，等不到才报错。

### 一次性迁移

首次打开库时（各记一次账，之后不再看）：

| 旧位置                     | 迁移方式                                                                | 原文件 |
| -------------------------- | ----------------------------------------------------------------------- | ------ |
| `<数据目录>/directives/`   | 递归导入，相对子目录成为 `folder`。`[directives].auto_import` 默认开     | 保留   |
| `<数据目录>/history.jsonl` | 导入 `runs`；`[history].enabled = false` 时跳过                         | 保留   |

导入**逐条报告**（`created` / `updated` / `skipped` / `failed`），同名默认不覆盖；失败的条目
带原因，可以在 daemon 日志或 `-v` 输出里看到。两个旧位置都是只读一次、写入一次账，
之后往旧目录里加文件**不会**自己冒出来——那正是「四套指令根」的老问题。

### 要做什么

- 升级一次（随便跑个 `corex directive list`、或起一次 daemon），确认库里内容没问题，再决定
  要不要清掉 `directives/` 与 `history.jsonl`。
- 靠 `directives/` 目录结构表达分组的：迁移后它会体现在条目自己的 `folder` 上。
- 想回到文件形态：`corex directive export --out <目录>`（默认不覆盖已有文件）。

## 2. 指令名必须过同一道门

`name` 从「文件主干」变成「库的键」，规则不变——**恰好一个普通路径组件**：`..`、分隔符、
盘符、绝对路径都不行（`a/b`、`..\evil`、`D:x` 全拒）。名字仍会被拿去拼临时文件名、写进
IPC 请求与执行日志，所以规则与 v12 一致，只是实现从 daemon 的 `check_directive_name` 换成了
`corex_store::validate_name`，CLI / daemon / MCP 共用一处。

**破坏面**：v12 里 `a/b` 会被当成「相对指令根的子路径」去找文件；v13 里它是**名字非法**
（400 / 退出码 2）。子目录不再是指令命名空间，而是 `folder` 这个字段。

## 3. IPC v13

### 请求形状

| 请求               | v12                                   | v13                                              |
| ------------------ | ------------------------------------- | ------------------------------------------------ |
| `directives`（原 `list_directives`） | `{dir?}` | `{}` |
| `read_directive`   | `{name, dir?}`                        | `{name}`                                         |
| `save_directive`   | `{name, definition, dir?}`            | `{name, definition, original_name?}`             |
| `delete_directive` | —                                     | `{name}`                                         |
| `import_directives`| —                                     | `{path, folder?, overwrite?, dry_run?}`          |
| `list_runs`        | `{name?, limit?}`                     | 不变                                             |

`dir` 参数整体消失：分组是条目自己的字段，不再靠目录表达。

### 回话形状

`directives`（原 `list_directives`）的条目：

```json
{
  "name": "build",
  "folder": "pack",
  "source": "C:\\work\\yaml\\pack\\build.yaml",
  "updated_at_ms": 1763818203123,
  "bucket": "logic",
  "summary": { "description": "打包", "step_count": 3, "input_count": 1, "trigger_count": 0 },
  "last_run": { "started_at_ms": 1763818203123, "ok": false, "duration_ms": 1321, "run_count": 4, "failed_count": 1 }
}
```

- `path` 没有了（指令不再住在文件里），`folder` / `source` / `updated_at_ms` 是新的。
- `summary` 只有模型解析得出来才有；解析失败的条目**照样列出来**（`summary: null`），用户正是
  要靠这份列表把它打开来修。
- `last_run` 与 v12 同形，仍是「最近一次 + 窗口内的次数」。

`read_directive` / `save_directive` 的回话：

```json
{
  "name": "build",
  "folder": null,
  "source": null,
  "created_at_ms": 1763818203123,
  "updated_at_ms": 1763818203123,
  "yaml": "name: build\nsteps:\n  - id: a\n    action: template.render\n",
  "definition": { "name": "build", "steps": [ … ] }
}
```

`text` 改名 `yaml`（它就是引擎序列化出来的**规范文档**，不是「某个文件的原文」），`path` 移除。

`save_directive` 的 `original_name` 是改名：给了它、且与 `name` 不同，daemon 在**一个事务**里
删旧键、写新键并沿用 `folder` / `source`。v12 那套「拿新名字另存一份文件、旧文件留在目录里
成了僵尸指令」的操作就此消失。

`import_directives` 的回话逐条报告：

```json
{
  "entries": [
    { "name": "build", "path": "C:\\work\\yaml\\build.yaml", "status": "created" },
    { "name": "old", "path": "C:\\work\\yaml\\old.yaml", "status": "skipped" },
    { "name": "broken", "path": "C:\\work\\yaml\\broken.yaml", "status": "failed",
      "error": "解析失败: expected ']', found <eof>" }
  ],
  "created": 1, "updated": 0, "skipped": 1, "failed": 1
}
```

`status` 取 `created` / `updated` / `skipped` / `failed`；只有 `failed` 带 `error`。
`delete_directive` 回 `{"name": "…"}`。

### 错误码

| 情形                              | 码  |
| --------------------------------- | --- |
| 名字非法、定义解析不了、动作没注册 | 400 |
| 权限声明不够                      | 403 |
| 指令不存在 / 文件不存在           | 404 |
| **名字已被占用**（改名 / 导入）   | 409 |
| 库读写失败（磁盘、锁超时）        | 500 |

409 是新加的：400 要改自己发的内容，409 得换个名字或先删旧的——调用方能做的事完全不同，
合成一个就只能靠猜消息文本。

### 要做什么

- 回包字段按上表改（`text` → `yaml`，去掉 `path`，补 `folder` / `source` / 时间戳）。
- 用 `dir` 分组的代码换成读条目自己的 `folder`。
- 「另存为新名字」的操作改成 `save_directive {name, original_name}`。
- 想区分「名字撞车」与「内容不合法」的，按 409 / 400 分流。

## 4. `corex directive`：库的增删改查

```text
corex directive list [--json]                     列出（名字、分组、步骤数、上次执行、描述）
corex directive show <名字> [--json]              规范化 YAML（--json 给模型）
corex directive new <名字> [-t 模板] [--force]     新建（写库）
corex directive edit <名字>                        $COREX_EDITOR / $EDITOR 打开并写回
corex directive rm <名字> [--yes]                 删掉
corex directive rename <旧> <新>                  改名
corex directive import <文件|目录> [--folder F] [--overwrite] [--dry-run]
corex directive export [<名字>…] [--out 目录] [--overwrite]
```

- `edit` 走**临时文件往返**：把库里的 YAML 写到 `<数据目录>/edit/<名字>.yaml`，等编辑器退出，
  重新解析 + 过「动作已注册 / 权限够」两道门，再写回库。没有配置编辑器时兜底一个**会阻塞**的
  编辑器（Windows `notepad`、别处 `vi`）——用 `start` / `open` 会打开 GUI 就返回，等不到改动。
  改坏了不会丢：文件留在原处，报错里给出路径。
- 在编辑器里改了 `name:` 就是改名（一次事务搬行，不留第二份）。
- `import` 是 YAML 进库的门：相对子目录成为分组，同名默认跳过，`--dry-run` 只说不做。
  导入前会过与 `run` 相同的两道门，所以写进去的都是跑得起来的。
- `export` 是出库的门：默认不覆盖已有文件。

### 老命令的去向

| v12                  | v13                                                     |
| -------------------- | ------------------------------------------------------- |
| `corex schedule`     | 保留：库里的指令名 + `examples/` 里还没进库的那几个      |
| `corex create`       | 保留为 `directive new` 的别名；**默认写进库**             |
| `corex create --dir` | 只写文件到该目录，不入库（脚手架 / 要一份可提交的 YAML）  |
| `corex edit`         | 保留为 `directive edit` 的别名                            |
| `corex history`      | 保留，读库里的 `runs`                                     |

### `--dir` 与 `--import` 的语义

- `--dir`（`run` / `schedule` / `validate` / `watch` / `cron`）：**库之外只读的回退搜索目录**。
  `run <名字>` 的顺序是「显式给的路径（存在就是它）→ 库 → `--dir` → `examples/directives`」。
  回退命中时会在 stderr 上说一句「库里没有这条指令，按文件执行 …」，免得用户以为跑的是库里那份。
- `--import <目录|文件>`（daemon 与 MCP）：启动时把它们导入一次，等价于
  `corex directive import`。v12 的 `--directives` 保留为别名，但含义从「换一个指令根」变成
  「导入一次」——指令的根只有一个。

### 还留着的文件入口

`corex run <路径>`、`corex run --file`、`validate <路径>` 与 IPC 的 `RunDirective.path` 都没变：
它们跑的是调用方明确给的那一份，**不入库**。演示、CI 自检、agent 生成的临时指令都靠它。

## 5. `corex paths` 换了一个字段

```json
{
  "version": "13.0.0",
  "data_dir": "C:\\Users\\Alice\\.corex",
  "database": "C:\\Users\\Alice\\.corex\\corex.db",
  "endpoint": "\\\\.\\pipe\\corex",
  "kind": "pipe",
  "token_file": "C:\\Users\\Alice\\.corex\\token"
}
```

`directives_dir` 换成 `database`（文件名为 `corex.db`，对齐 i-thinking 的 `i-thinking.db`）：宿主该显示、该交给外部工具的是**库文件**，而不是一个
已经不参与读写的目录。宿主读它的方式与 daemon / CLI 完全一致（同一个 SQLite 文件），
所以「明明改了却没生效」不会再来自两棵树。

**要做什么**：宿主里读 `directives_dir` / `directives_db` 的地方换成 `database`；把它显示成「指令库」而不是
「指令目录」。（Studio 侧已按此实现，见 [编辑器集成](../integration/编辑器集成.md)。）

## 6. 配置：`[directives]` 新段，`[history].file` 换了含义

```toml
[directives]
# 首次打开库时，把 <数据目录>/directives 里的 YAML 一次性导入（默认 true）
auto_import = true
# 库为空时写入起步指令（默认 true）
seed = true

[history]
# 还记不记执行日志（默认 true）。关掉 = 不记，而不是记到别处
enabled = true
# 旧版 JSONL 账本的位置：v13 里它只剩「首次打开时一次性导入」这一个用途
file = "history.jsonl"
```

**破坏面**：`[history].file` 不再决定「日志写在哪」——写入落点是库里的 `runs` 表，
daemon / CLI / MCP / 宿主读的是同一份。另外，`[directives]` 是**新键**，配置里写了未知键
会被拒（`deny_unknown_fields`），所以 v12 的配置文件可以原样用，反过来（v12 的二进制读 v13 的
配置）会报错。

---

## 7. 没变的部分

- **执行模型**：`Pipeline`、两道门（`validate_registered` / `validate_allowed`）、退出码
  （2 = 写错、3 = 被拒）与 `audit.jsonl`（步骤级审计）都没动。
- **`run --remote`**：仍然把名字交给 daemon，由它从**自己的库**里取。库是同一份文件，
  所以「CLI 跑的」与「daemon 跑的」是同一条指令。
- **触发器**：`watch` / `cron` 仍按指令名登记作业；差别在于 supervisor 每次触发都从库取，
  于是 `corex directive edit` 改完，**下一次触发**就会用新版本。
- **MCP**：`corex_run_directive` 仍接受 `name` / `path` / `input`；`name` 现在查库，`path`
  是 ad-hoc 文件。
