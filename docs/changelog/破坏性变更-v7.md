# 破坏性变更 — Corex v7

v7 把 watch 的计时收敛成**防抖门 → 节流门**两级逻辑门，并把执行时机（边沿）
开放为配置。指令 YAML 的**既有键语义不变、默认行为不变**——唯一的破坏面是
`corex-engine` 上那几个碰巧是 `pub` 的内部计时符号。

---

## watch 计时模块：`watch::throttle` → `watch::gate`（v7.0.0）

| v6 公开路径                                                 | v7                                                 |
| ----------------------------------------------------------- | -------------------------------------------------- |
| `corex_engine::watch::throttle`                             | `watch::gate`，且**不再公开**（降为 `pub(crate)`） |
| `corex_engine::watch::throttle::InvokeThrottle`             | 移除（内部改为 `Gate` / `Chain`）                  |
| `corex_engine::watch::throttle::TriggerDecision`            | 移除（内部改为 `Decision`）                        |
| `corex_engine::watch::throttle::wait_for_trailing_deadline` | 移除（worker 改为单一定时器 + 两扇门的待执行期限） |

这些类型是**内部计时实现**，v6 里只是碰巧没有收窄可见性。新增的公开 API 是：

- `corex_engine::Edge`（`leading` / `trailing` / `both`）
- `corex_engine::WatchConfig::{debounce, throttle}`
- `corex_engine::{DEBOUNCE_EDGE, THROTTLE_EDGE}`

只有直接引用过上面那几个符号的嵌入方需要改；CLI / daemon / IPC 不受影响。

---

## 时间轴：FS 安静期 → 逻辑防抖门

`debounce_ms` 过去是 `notify_debouncer_full` 的**文件系统安静期**，现在它是
**逻辑防抖窗口**；FS 层退化为事件合并（去重 / 重命名）：

```text
v6: FS 事件 ──FS 安静期(debounce_ms)──► 触发 ──节流(throttle_ms, leading+trailing)──► run
v7: FS 事件 ──合并(≤25ms)──► 防抖门(debounce_ms, debounce)──► 节流门(throttle_ms, throttle)──► run
```

这是新增 `debounce: leading` / `both` 的前提：`notify_debouncer_full` 只能在
安静期**之后**回调，天生做不了 leading。

默认值（`debounce: trailing` + `throttle: both`）与 v6 行为一致，实际差别只有：

- 总延迟多出 ≤ 25ms 的事件合并窗口（安静期改由逻辑门判定）；
- 事件风暴不再被 FS 层长时间压住，但分类 / glob 的工作总量不变（同一批事件，只是分批到达）。

## 配置：`debounce` / `throttle`（新增，非破坏）

```yaml
triggers:
  - type: watch
    paths: ['./src']
    debounce_ms: 300
    debounce: trailing # leading | trailing | both（默认 trailing）
    throttle_ms: 1200
    throttle: both # leading | trailing | both（默认 both）
```

两级是 lodash 的**同一台状态机**（`_.throttle(fn, w, o)` === `_.debounce(fn, w, { ...o, maxWait: w })`），
`debounce` / `throttle` 只设置各自的 `leading` / `trailing`，三级取值**两级通用**：

| 取值       | 等价 lodash                      | 首次触发 | 窗口内再有触发             |
| ---------- | -------------------------------- | -------- | -------------------------- |
| `leading`  | `leading: true, trailing: false` | 立即执行 | 不产生后续执行 ⚠️          |
| `trailing` | `leading: false, trailing: true` | 不执行   | 合并，窗口结束时执行一次   |
| `both`     | 两者皆是（lodash 默认）          | 立即执行 | 合并，窗口结束时再执行一次 |

- 两级的差别来自 `maxWait`（防抖没有、节流 `= throttle_ms`），**不是**来自边沿。
- `leading` 是唯一**会落后**的取值（窗口内的触发不产生补跑 ⇒ 产物可能长期陈旧），注册时会打一条 warn。
- 唯一的 corex 差异：流水线是**单飞**的（一次只跑一轮）。边沿放行的执行若撞上正在跑的那轮，会等它收尾再执行——只**推迟**、不并发；`leading` 在窗口内该丢的照丢。
- 详见 [指令 YAML · 防抖与节流](../reference/指令YAML.md#防抖与节流)。

## CLI 交互改造：进度成为一等公民（v7.1.0）

这一节列的都不是引擎语义变更，而是**面向使用者的行为变化**，其中两条会影响既有脚本。

### `corex run` 的默认日志级别改为 `warn`

`[logging].level` 从 CLI 的默认级别来源退为**只作用于守护进程**。

原因是同一条事实不该在两个通道里各说一遍：CLI 现在有专门的进度通道（stderr 上的
`✓ 动作  步骤  耗时` 行 + spinner）与结果通道（stdout），而 `corex_engine::audit`
还会在每个步骤前后各发一条 `info` 日志。两个通道讲同一件事的结果，是 `corex run` 的
进度与结果被十几行 `INFO corex_engine::audit:` 埋掉。

| 想要         | 做法                                           |
| ------------ | ---------------------------------------------- |
| 进度（默认） | `corex run <名称>`                             |
| 关掉进度     | `corex run <名称> --quiet`                     |
| 引擎日志     | `corex -v run <名称>`（debug）/ `-vv`（trace） |
| 环境变量     | `COREX_LOG=corex_engine=debug`                 |

**受影响的情况**：以前靠 `[logging] level = "debug"` 从 CLI 拿调试日志的用法，现在要改用
`-v` 或 `COREX_LOG`。守护进程的 `daemon.log` 不受影响，`[logging]` 对它照旧生效。

### `corex run` 省略名称时变成交互式，名称支持模糊匹配

`corex run` 的 `target` 从必填改为可选；不给名称会在终端里列出指令让用户挑。
给了名称但没有精确命中时，错误信息附带「最接近的」候选名——不再只报一句「指令不存在」。

非终端环境（脚本 / CI）里省略名称是用法错误（退出码 2），不会静默挑一个跑。

### `corex run` 新增 `--dry-run` / `--json-events` / `--quiet` / `-y`

- `--dry-run`：解析 + 确认动作已注册 + 过一遍**运行时权限门**，打印将要执行的步骤树，不执行。
  它与 `--strict` 不是同一道门：后者是企业的“必须声明 permissions”，真跑并不要求。
- `--json-events`：stdout 变成 NDJSON 事件流（`step_start` / `step_progress` / `step_end`
  / `result`，失败时 `error`）。最终结果不再是独立的 JSON 文档，而是最后一条事件。
- `--quiet`：不挂进度上报口。
- `-y` / `--yes`：不交互追问，缺指令名或必填输入直接报错。

### `corex actions` 接受可选的动作 id

`corex actions`（无参数）输出不变。`corex actions file.copy` 会打印参数表（名字 / 类型 /
必填 / 默认 / 说明）、权限类别，以及一段可直接粘进 `steps:` 的片段。

### 新命令

| 命令                            | 说明                                                          |
| ------------------------------- | ------------------------------------------------------------- |
| `corex schema [--write <路径>]` | 输出指令 YAML 的 JSON Schema（编译期内嵌，不引入 `schemars`） |
| `corex completions <shell>`     | 用 `clap_complete` 生成补全脚本                               |
| `corex doctor`                  | 自检数据目录、配置、守护进程、动作与指令；有问题退 1          |

### `corex create` 重做

- 新增 `-t` / `--template`：内置 `hello` / `http` / `file` / `shell` / `cron` / `watch`，
  也可以给一个目录或 YAML 路径直接拷贝。
- 无 `-t` 且在终端里时进入向导：选模板，或「只放一个动作」——从注册表挑动作、逐个问必填
  参数，并**按动作声明的权限自动写好 `permissions:`**。
- 名称从必填改为可选（省略则在终端里问）。
- 目标已存在时在终端里问一句要不要覆盖，不再直接失败。
- 生成的 YAML 顶部带 `# yaml-language-server: $schema=./directive.schema.json`，并在同一
  目录放一份 schema 副本，编辑器立刻有补全与校验。

### `corex validate --watch`

盯着一个指令 YAML，每次保存后重新校验；校验失败只打印错误、不退出循环，Ctrl+C 结束。

### `corex repl` 重做

- 首屏给出：版本、指令数（自有 / examples）、动作数、最近跑过的几条指令。
- **不再有第二套语法**：一行文本切词后重新交给 clap 与 CLI 的 `dispatch`，因此命令行里
  有的子命令 REPL 里都有；只敲指令名等价于 `run <指令名>`。
- `rustyline`：Tab 补全（指令名 + 子命令）、↑/↓ 历史、跨会话历史（`<数据目录>/repl_history`）、
  Ctrl+C 清行（连按两次退出）、Ctrl+D 退出。
- 非终端输入时退回逐行执行的朴素循环，`echo schedule | corex repl` 依然可用。

### 新增 API（`corex-core`）

`progress::{Observer, Spot, Mark, Unit}`、`ExecutionContext::{observer, chunk, enter_step,
leave_step}`、`corex-engine` 的 `Pipeline::with_observer`。

`Mark` 带 `unit`（`Bytes` / `Items`）：递归删除上报的是条目数，不是字节数。

### 动作行为变化

- `file.copy` 在有上报口时改走 1 MiB 分块拷贝（能出百分比）；没有上报口时仍是
  `tokio::fs::copy`，平台最优路径不受影响。
- `file.remove` / `dir.remove`（`recursive: true`）在删除前统计条目数并上报为总量。

### 新依赖

`rustyline 18`（REPL 行编辑）、`clap_complete 4.6`（补全脚本生成）。两者都不进入
`corex-daemon`，也不改变 CLI 依赖树里「无 wasmtime / schemars / pdfium」的约束。

## daemon 侧的进度流（v7.1.0）

进度此前只存在于 CLI 的进程内（`Pipeline::with_observer` + 渲染器），**daemon 一个字节都不产出**：
`bins/daemon` 的 `run_directive` 不挂上报口，`invoke_action` 更是绕过了 `Pipeline` 直调动作，
所以 `ctx.chunk()` 全是空操作；IPC 的 `serve_ipc` 又是「一问一答」，没有通道把它送出去。

现在补上了完整的四段：协议 → 服务端推送 → daemon 接线 → 客户端消费。

### 协议：新增 `stream` 开关与 `event` 帧

- `Request::RunDirective` 与 `Request::Invoke` 增加 `stream: bool`（`#[serde(default)]`）。
- `Response` 增加 `Event { id, progress }`：**中间帧**，只在请求置了 `stream` 时出现，
  一定排在终帧（`ok` / `error`）之前。
- `ProgressEvent`（`corex-ipc`）：`step_start` / `step_progress` / `step_end`，
  与 `corex_core::progress::Observer` 的三个方法一一对应（`replay` 可无损重放）。

**兼容性**：不置 `stream` 的客户端拿到的线与旧版**完全一致**（wire 层无破坏）。
需要改的是 `Response` 的**穷尽匹配**——嵌入方若有 `match` 未覆盖新变体，会在编译期被拦下，
这是有意为之：漏掉 `event` 帧的读循环会把中间帧当成回答。

### 需要改动的 Rust API（`corex-ipc`）

| v7 之前                                      | 现在                                                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `Transport::send`（唯一必需方法）            | `Transport::send_events(request, sink)` 是唯一必需方法；`send` 变成它的默认实现（用一个丢弃帧的落点） |
| `serve_ipc(endpoint, FnMut(Request) -> Fut)` | `serve_ipc(endpoint, FnMut(Request, Outlet) -> Fut)`；`Outlet` 用于推帧                               |
| `<Transport>::serve(path, handler)`          | 同上，handler 多收一个 `Outlet`                                                                       |

本仓只有 daemon 一个调用点，改动已随之完成。新增的公开项：
`corex_ipc::{ProgressEvent, FrameSink, Outlet, Replay}`。

### daemon

- `StreamObserver` 实现 `Observer`，把 `begin` / `chunk` / `end` 变成 `event` 帧。
  **一帧都不 `await`**：`parallel` 分支会并发调用，队列满即丢帧——一条渲染慢的客户端
  不该让流水线慢下来。
- `run_directive` 在 `stream` 时挂上报口。
- `invoke_action` 补上了 `ctx.enter_step()` 与 begin / end：单动作直调绕过了 `Pipeline`，
  不补这一步动作上报的分块进度会**静默落空**。

### CLI：`corex run --remote`

新增 `--remote`（与 `--dry-run` 互斥）：把指令名交给 `corex-daemon` 执行，把推回来的帧
经 `Replay` 喂给**同一个** `Steps` / `Events` 渲染器。于是：

```text
corex run hello --remote              # 人类可读的进度行 + 结果 JSON
corex run hello --remote --json-events # NDJSON 事件流
corex run hello --remote --quiet       # 连帧都不要（daemon 因此连观察者都不挂）
```

IPC 的错误码折回 CLI 的退出码表（403→3、400/404→2、其余→1），所以
`corex run --remote` 与本地 `corex run` 对同一种失败给出同一个数字。

### `--json-events` 的判别字段由 `event` 改为 `kind`

负载就是 `ProgressEvent` 的 JSON，与 daemon 推回的帧**同一套词汇**；`result` / `error` /
`plan` 也多了一个 `kind`。`unit` 由字符串（`"bytes"`）改由 serde 产出（同值）。

### 测试

- `crates/ipc/tests/streaming.rs`：真实平台传输（命名管道 / Unix socket）上的帧顺序、
  以及「不置 `stream` 就一帧都没有」的向后兼容断言。
- `bins/daemon/tests/streaming.rs`：拉起**真实 `corex-daemon` 进程**，验证
  `invoke` 的分块进度、`run_directive` 的每步帧，以及一问一答路径不受影响。

## IPC 端点改为平台默认（v7.1.0）

随仓库发货的 `config/corex.toml` 里写着 `socket_path = "corex.sock"`，那是个 **Unix**
socket 名字。Windows 上底层 `CreateNamedPipe` 会以「文件名、目录名或卷标语法不正确」
（`os error 123`）失败——从仓库根目录跑 `corex daemon run` 直接起不来，而报错完全
指不出原因。

现在：

- `config/corex.toml` 里 `socket_path` **注释掉了**，注释说明「省略即平台默认」
  并给出两个平台各自的值。默认端点只有一个来源：`corex_ipc::ipc_endpoint`。
- 端点解析（相对路径拼接、管道路径识别、平台校验）从 CLI 与 daemon 的两份副本
  收敛到 `corex_ipc::resolve_endpoint` / `resolve_data_relative`。
- Windows 上给了非管道路径会**当场报错**，而不是等到底层抛一句 os error：

  ```text
  错误: 配置错误: 端点无效: Windows 上的 IPC 端点是命名管道，不能是文件路径:
        <data>\corex.sock（写成 \\.\pipe\corex，或省略该项以用平台默认）
  ```

  CLI 走 `EngineError::Config`（退出码 2）；daemon 仍是 1（其退出码按既有约定
  不是脚本契约）。

- `corex doctor` 新增「IPC 端点」一行，这类配置问题因此不必等到启动 daemon 才暴露。

**受影响的情况**：依赖 `socket_path = "corex.sock"` 这个字面默认值的配置。Unix 上行为
不变（解析结果仍是 `<数据目录>/corex.sock`）；Windows 上以前是启动失败，现在是启动成功
并走 `\\.\pipe\corex`。
