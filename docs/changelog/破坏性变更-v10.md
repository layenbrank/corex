# 破坏性变更 — Corex v10

v10 把 v9 落下的几处**收尾**做完了：一条连接上真的能有多条请求在飞、连接侧找 token 只有一处
规则、`list_actions` 的目录带上版本号。

与 v9 相比，破坏面很小：**线格式只有一处变化**（第 1 节），其余都是行为变更——用现成
`corex-daemon` 二进制的人不会撞上编译错误。

---

## 1. `list_actions` 回的是**目录文档**，不再是动作数组

`data` 从「动作数组」变成「整份目录文档」，多了一层 `actions`，并带上 `version` / `count` /
`bucket`——与 `corex actions --json` 是同一份 `corex_registry::catalog::document`。

| v9                                            | v10                                                        |
| --------------------------------------------- | ---------------------------------------------------------- |
| `data[].id`                                   | `data.actions[].id`                                        |
| 拿不到版本号                                  | `data.version`（产出这份目录的 corex 版本）                |

元素的字段一个没动（`id` / `name` / `description` / `bucket` / `params` / `permissions` /
`input_schema`）。用 [`packages/corex-client`](../../packages/corex-client/README.md) 的话不用改：
`actions()` 仍然回数组，要版本号用 `catalog()`。

**为什么要动**：MCP 那类宿主需要在参数表变化时重拉，而 v9 的响应里没有版本号——只有 CLI 那份
`--json` 有。这次让两边共用同一个文档，顺带把「谁该重拉」这件事变成可判断的。

---

## 2. 同一条连接上可以同时有多条请求在飞（v9 的承诺，这一版才真的做到）

v9 的协议文档写了「一条连接上可以同时有多个请求在飞」，但服务端仍是**逐行读、跑完一条才读
下一条**：一条几分钟的指令期间，同一个客户端连 `ping` 都发不出去（JS 客户端按一条连接多路复用
写，于是主机的探活会以「请求 ping 超时」失败——看起来像失联）。

v10 把每个请求放进自己的任务，写回由一条队列独占：

| 事项         | v10 的行为                                                         |
| ------------ | ------------------------------------------------------------------ |
| 读请求       | 读到就推进，不再等前一条跑完                                        |
| 写回         | 一条连接一条写队列；**一个请求的帧仍排在它自己的终帧之前**           |
| 跨请求顺序   | **不保证**——按 `id` 归位才是正确读法（帧本来就带 `id`）              |
| 收 `bye`     | 服务正要退：本连接上还在跑的请求会被**中止**（它们也没有答案可送）  |
| 对端断开     | 先把在途请求的答案写完，再结束这条连接                              |

⚠️ 如果宿主依赖「同一连接上我发第二条之前第一条已经回完」，现在不再成立。Rust 侧
`corex_ipc::Transport::send` 是每请求新建连接，不受影响；受影响的是手写多路复用的宿主
（含 `packages/corex-client` 的所有用例，这条正是它需要的）。

---

## 3. 连接侧找 token 只有一处规则

v9 的三方顺序不一致：daemon 是「`COREX_TOKEN` → 配置 → 文件」，CLI 只看「环境变量 + 文件」，
JS 客户端还有自己的一套。于是**在配置里设了 `[daemon].token` 起的 daemon，在 CLI 眼里永远是
「已停止」**（`corex daemon status`、`corex doctor` 都会这么报）。

v10 把连接侧收敛成 `corex_ipc::find_token`：

| 顺序 | 来源                                        |
| ---- | ------------------------------------------- |
| 1    | `COREX_TOKEN`（CLI）/ `connect({ token })`（SDK） |
| 2    | 配置 `[daemon].token`                        |
| 3    | **端点记录里的 `token_file`**（daemon 说它的 token 在哪个文件） |
| 4    | `<数据目录>/token`（只在**没有**端点记录时才看） |

附带两条约束，宿主实现自己的客户端时照做即可：

- 端点记录在、但里面**没有** `token_file`，说明 daemon 的 token 来自第 1 / 2 档（值属于调用方，
  不会被复制进记录）。此时**不要**去读 `<数据目录>/token`：那是**上一个** daemon 留下的东西，
  拿它去连只会得到一句 401。
- token 来自配置文件时，JS 客户端看不到（它不解析 TOML）：把值显式传给 `connect({ token })`，
  或设 `COREX_TOKEN`。

---

## 4. 失败回答的错误码按**错误类型**给，不再按消息文本猜

v9 的 daemon 用 `message.contains("指令未找到")` / `contains("权限")` 反推 `code`。现在照
`ExitStatus::read` 的做法遍历 `anyhow` 链逐个 `downcast`：

| `code` | 什么时候 |
| ------ | -------- |
| **400** | 参数写错（`invalid_params`）、指令解析失败、用法 / 配置错误、动作未注册 |
| **401** | token 不对（不变） |
| **403** | 门禁拒绝：`strict_permissions`、`plugins.disabled*` |
| **404** | 用户点名的**指令**不存在；路径沙箱外的那类请求仍是 403 |
| **500** | 其余：动作跑了但没成功（`io` / `timeout` / 运行期找不到文件…） |

两处不会再混：**动作的 `not_found`**（文件 / 窗口没了）是 500，**引擎的 `not_found`**（指令不存在）
才是 404；消息里出现「权限」也不再等于 403。

---

## 5. 端点记录写在**端点就绪之后**

`endpoint.json` 现在由 `serve_ipc_ready` 的回调写出（socket / 管道**已经 bind** 之后）：
「有记录」因此等于「端点正听着」，而不是「有人正打算监听」。嵌入方用 `serve_ipc` 时行为不变
（它不写记录）；要这个保证就用 `serve_ipc_ready`（新增，签名多一个 `FnOnce()` 回调）。

---

## 6. 两处不涉及契约、但值得知道的修复

| 变更 | 说明 |
| ---- | ---- |
| **管道回显不再重解整段** | `shell.run` / `exec.run` 的实时回显过去每读 8 KiB 就把已收到的全部重解一遍（O(n²)：61 MB 输出要 96 秒）。现在按流增量解码，同一份输出 1~2 秒 |
| **JS 客户端的跨块解码** | 一帧被读块从汉字中间切开时不再变成替换字符（`U+FFFD`）。此前 JSON 仍然合法，所以坏掉的是**内容**而不是解析——静默 |
| **`corex_ipc::find_token`** | 新增：连接侧找 token 的唯一实现（CLI 与文档都指向它） |
| **`corex_ipc::serve_ipc_ready`** | 新增：端点 bind 之后先回调再服务（`serve_ipc` 保持不变，等价于回调什么都不做） |
