# 破坏性变更 — Corex v6

v6 是在 v5 之上的一轮**收敛**：统一 `find_*` 查询 API、用 `throttle_ms` 取代 `cooldown_ms`、把错误分类变成稳定契约、审计记录改为 typed 构造。

**没有** v5 的 IPC / YAML 兼容层。请整包升级，不要混用 v5 与 v6 的引擎与 daemon。

---

## 概览

| 范围         | v5                                         | v6                                                  |
| ------------ | ------------------------------------------ | --------------------------------------------------- |
| 查询 API     | `get_variable` / `get_path` / `get_action` | **`find_variable` / `find_path` / `find_action`**   |
| watch 节流   | `cooldown_ms`（弃用但仍解析）              | **`throttle_ms`**；`cooldown_ms` 直接报错，无 alias |
| 错误分类     | 依赖 `Debug` 输出 / 字符串匹配             | **`kind()`** 返回稳定机器可读字符串                 |
| 审计 / 历史  | 逐字段手写                                 | **`AuditEntry::from_engine` / `from_action`**       |
| 格式化与门禁 | 各自风格                                   | 全仓 rustfmt + pre-commit / cargo-deny / typos      |

---

## 查询 API：`get_*` → `find_*`（v6.0.0）

命名收敛，**不保留旧名**：

| v5                                         | v6                                | 位置           |
| ------------------------------------------ | --------------------------------- | -------------- |
| `Value::get_path`                          | `Value::find_path`                | `corex-core`   |
| `Value::get_path_mut`                      | `Value::find_path_mut`            | `corex-core`   |
| `ExecutionContext::get_variable`           | `ExecutionContext::find_variable` | `corex-core`   |
| `ActionStore::get_action`                  | `ActionStore::find_action`        | `corex-core`   |
| `find_cron_trigger` / `find_watch_trigger` | 同名（v6 起为规范名）             | `corex-engine` |

嵌入 Corex 的应用需要改调用点。这是编译期错误，不会静默改变行为：

```rust
// v5
let name = ctx.get_variable("user").and_then(Value::as_str);
// v6
let name = ctx.find_variable("user").and_then(Value::as_str);
```

Directive YAML 里的 `{{...}}` 占位符语法**未变**，只有 Rust API 受影响。

## watch 触发器：`cooldown_ms` 被拒绝（v6.0.0）

旧的 `cooldown_ms` 语义含糊（既是去抖又是节流），v6 把它拆成两个明确的阶段：

```text
FS 事件 ──debounce(debounce_ms)──► trigger ──throttle(throttle_ms)──► run_directive
```

| 键            | 规则                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------ |
| `debounce_ms` | 事件聚合窗口                                                                               |
| `throttle_ms` | 运行节流间隔（leading + trailing），**必须 > 0**；缺省为 `max(debounce_ms * 2, 1000)`      |
| `cooldown_ms` | **已移除**。保留会解析失败：`watch.cooldown_ms 已移除，请改用 throttle_ms（无兼容 alias）` |

YAML 迁移：

```yaml
# v5
triggers:
  - type: watch
    paths: ["src"]
    debounce_ms: 500
    cooldown_ms: 2000

# v6
triggers:
  - type: watch
    paths: ["src"]
    debounce_ms: 500
    throttle_ms: 2000
```

若原先依赖 `cooldown_ms` 的默认值，删掉该键即可——v6 的默认值是 `max(debounce_ms * 2, 1000)`，对多数场景更保守（即触发更少）。

## 稳定错误分类（v6.0.0）

`ActionError` 与 `EngineError` 现在都提供 `kind()`，返回**稳定**的机器可读字符串，供审计、历史与 `on_error` 分支使用。不要再匹配 `Debug` 输出。

| `ActionError::kind()` | 场景                                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| `permission_denied`   | 权限 / 策略拒绝                                                                                     |
| `timeout`             | 超时                                                                                                |
| `invalid_params`      | 缺参或参数非法                                                                                      |
| `not_found`           | 目标不存在                                                                                          |
| `disabled`            | 动作被禁用                                                                                          |
| `io`                  | 文件系统错误                                                                                        |
| `execution`           | 其余执行失败                                                                                        |
| `ui_*`（动态）        | `ExecutionFailed` / `Other` 带上 UI 细化码时返回它（如 `ui_login_pending`），否则回落到 `execution` |

| `EngineError::kind()` | 场景                                       |
| --------------------- | ------------------------------------------ |
| `not_registered`      | 动作未注册                                 |
| `not_found`           | 指令 / 文件不存在                          |
| `parse`               | YAML 解析失败                              |
| `resolve`             | 变量未定义 / 解析失败                      |
| `control_flow`        | 条件与流程控制错误                         |
| `config`              | 配置错误                                   |
| `usage`               | 调用方式错误（本次新增，见上方退出码小节） |
| `io`                  | 文件系统错误                               |
| `execution`           | 其余                                       |

配套：`is_permission_denied()` 用于区分"策略拒绝"与"执行失败"——审计的 `denied` 字段即由此而来。

## 审计与历史：typed `AuditEntry`（v6.0.0）

审计记录改为从 typed error 构造，字段与错误分类对齐：

| 方法                           | 用于                                            |
| ------------------------------ | ----------------------------------------------- |
| `AuditEntry::from_engine(...)` | Pipeline 步骤（`EngineError`）                  |
| `AuditEntry::from_action(...)` | Daemon IPC `invoke` 与 UI 探测（`ActionError`） |

记录字段新增/明确了 `error_kind`、`denied`、`ui_phase`、`error_code`、`selector_hint`（全部为 `Option`，序列化时省略）。审计仍然**不含**正文、OCR 结果与剪贴板内容。

直接手写 `AuditEntry { .. }` 的代码需要改为调用上述构造函数，否则会丢掉 `error_kind` / `denied` 的推导。

## 非破坏性变更（v6.0.0）

以下变更不需要迁移动作：

- `fix(engine)`：修复 watch 竞态；cron 退出时正确 unregister。
- `fix(cli)`：CLI 写入审计的路径与服务端对齐（此前 CLI 与 daemon 的审计字段可能不一致）。
- `style`：全仓 rustfmt，仅影响格式。
- `tooling`：引入 pre-commit、cargo-deny、typos 与 git-cliff。

## 自更新（v6 之后的版本引入）

`corex update` 让更新变成一条命令（GitHub Releases → SHA-256 校验 → 原子替换）。它**不是**破坏性变更，但会改变你的升级方式：

```powershell
corex update --check   # 只报告
corex update           # 安装
```

- 只替换 `corex.exe`，`corex-daemon.exe` 不动；daemon 有变更时会提示重启。
- 企业 / 气隙部署在 `config/enterprise.toml` 里已设 `[update] enabled = false`。
- 旧版本（≤ v6.0.1）没有该命令，需先用 `install.ps1` 升级一次。

详见 [自更新](../reference/自更新.md)。

## 架构收敛（v6.0.1 之后，未发布）

一轮对标大型 CLI 的架构整理。**引擎与指令 YAML 均无变化**，但脚本可见的契约有变更。

### 退出码：不再一律为 1

此前所有失败都退 1，脚本无法区分「指令跑失败」「参数写错」「被策略拒绝」。现在：

| 退出码 | 含义                                                               |
| ------ | ------------------------------------------------------------------ |
| 0      | 成功                                                               |
| 1      | 命令运行了但失败                                                   |
| 2      | 用法错误：参数 / 指令不存在、YAML 解析失败、**配置无效**           |
| 3      | 被策略拒绝：`permission_denied`，或动作被 `plugins.disabled*` 关掉 |

两个细节值得写下来，因为它们曾经是错的：

- **管道被提前关闭仍然是 0**，但不再靠「退出前发现 stdout 已关就报成功」这种短路实现——那会把任何「先输出、后失败」的命令（例如 `attach` 打印完头部再读日志失败）降级成 0。现在 `output` 层把 EPIPE 当作已处理的写失败吞掉，命令自身的成败因此如实反映在退出码上；日志跟随也会在检测到 `STDOUT_CLOSED` 时结束，而不是继续轮询一个没人读的管道。
- **被管线包裹的权限拒绝也要退 3**。`EngineError::kind()` 对 `StepFailed` / `Action` 会委托给内层 `ActionError`，但**不能靠这个字符串选桶**：`not_found` 在动作侧是「文件/窗口不存在」（运行失败），在引擎侧是「指令不存在」（用法错误），同一个字符串指向相反的两类。`ExitStatus::read` 因此在同一分支里按**类型**取出内层错误、再用动作那张表。CLI 自身的错误也一律**复用既有词汇**、不另立类型：门控拒绝是 `ActionError::PermissionDenied`，用法错误是新增的 `EngineError::Usage`（只是并进 `kind()` 表的一个值），否则 `bail!` 与 `validate_permissions` 的拒绝会一律落进 1。

**daemon 不区分这些码**：`corex-daemon` 启动失败（含配置无效）一律退 1。它是由监督进程拉起的服务，退出码不是脚本契约；分类表（`ExitStatus` 及其 `read`）只存在于 `bins/cli`。将来若有消费者确实需要 daemon 分类，再把那张表共享出去——现在把它下沉到核心库，只会把「进程退出码」这种宿主关切混进运行时抽象里。

### stdout 只承载结果

- **所有日志改到 stderr**。此前 `tracing` 默认写 stdout，`corex run x --json | jq` 可能被日志污染。
- 所有命令输出走单一出口：管道被提前关闭时安静退出 0，不再以非正常状态终止。

### 配置：失败即报错，不再静默回落

- 配置文件**存在但解析失败** → 命令失败（退出码 2）。此前会**静默**使用默认值，可能无声关掉 `strict_permissions`。
- **显式给出的 `--config` 必须存在**：路径拼错时命令报错（退出码 2），不再“找不到就用默认值”——候选路径（未指定 `--config` 时）可以都不存在，但用户亲口指定的一个不行。
- **未知 section / 键会被拒绝**（此前被忽略）——拼错的 `strict_permissons` 现在会报错。
- 新增 `--config <PATH>`（CLI，与 daemon 对齐）；`corex validate` **不带路径**时检查配置。
- `corex`、`corex-daemon`、`corex ui` 读**同一份**配置。此前 `corex ui` 只认识 2 个 section、`runtime` 只有 5 个字段，`[history]` / `[update]` / `[daemon]` / `[logging]` 与 `filesystem_roots` 对它完全不可见。

### `permission_denied`：策略拒绝现在真的会中止

`plugins.disabled` / `disabled_actions` / `strict_permissions` 三道运行时闸门此前返回通用执行错误，因此引擎的「权限拒绝不被 `on_error: continue` 吞掉」规则**拦不住它们**——写了 `on_error: continue` 的步骤可以绕过 `strict_permissions`。现已统一为 `permission_denied`。

### WASM：CLI 不再链接 wasm 运行时

`corex-registry` 的 `full` feature 改名为 **`all-actions`**，且**不再包含 `wasm`**。`corex run` 在进程内执行指令、从不加载插件（`discovery::discover` 只在 daemon 调用），所以 CLI 链接 wasmtime 属于死重：wasm / cranelift 家族在 CLI 的依赖树里从 **46 个 crate 降到 0**（同一命令、同一会话内实测）。`wasm` 由 `corex-daemon` 单独启用，**插件能力不变**。

嵌入方若写死 `features = ["full"]`，需改为 `["all-actions"]`；需要插件再加 `"wasm"`。

### 新增质量闸门

`.github/workflows/quality.yml`：`fmt --check`、`clippy -Dwarnings`、feature powerset、MSRV（新增 `rust-version = "1.95"`）、`cargo deny`、`typos`。这些此前只存在于**需手工 `pre-commit install`** 的配置里，等价于没跑。

补充两处：`clippy` 追加 `-p corex-engine --features schema --all-targets -- -Dwarnings`（`cargo clippy --workspace` **不会**编译默认关闭的特性，那部分代码否则永远不被 lint），以及断言 `schemas/directive.schema.json` 与类型一致。

### 权限声明：从 id 表搬到动作本身

`permission_kind_for(action_id)` 这张「动作 id → 权限」表**已删除**，改由动作自己声明：

| 位置       | v6.0.1 之后                                                                              |
| ---------- | ---------------------------------------------------------------------------------------- |
| 声明       | `Action::permissions() -> PermissionSet`（**无默认实现**）                               |
| 查询       | `ActionStore::permissions_of(action_id)`                                                 |
| 运行时闸门 | `check_runtime_allowed(config, store, action_id)`                                        |
| 指令校验   | `Permissions::allows_action(store, action_id)`、`validate_permissions(store, directive)` |

换掉它的理由不只是整洁：旧表以 `_ => None` 兜底，**新动作忘了登记就会按「无需权限」放行**——`strict_permissions` 形同虚设。现在漏写是编译错误。

`PermissionKind` 仍作为单值枚举存在（对应指令 `permissions:` 的各个布尔项），并新增 `PermissionSet` 位集合作为**声明**类型：一个动作可以同时需要多类权限，单值类型在类型层面就表达不了。

`Permissions` 的拒绝信息现在会列出缺少的类别（`指令未声明权限 filesystem+capture 以执行 capture.crop`）。

同时删除 `corex_engine::audit::is_sensitive_action`：它没有任何生产调用方，审计的「不出现参数内容」是由「从不记录 params」这一结构保证的，与该集合无关。

### `capture.*` / `clipboard.set` 的权限声明被修正

旧表每个动作只能给**一个**类别，于是这几个动作的声明都不对——**方向还相反**：有些漏报了、有些多报了。

| 动作                 | 迁移前       | 现在                       | 为什么                                             |
| -------------------- | ------------ | -------------------------- | -------------------------------------------------- |
| `capture.screenshot` | `capture`    | `capture` + `filesystem`   | 真的截图**并**写文件：旧声明漏了文件写入           |
| `clipboard.set`      | `clipboard`  | `clipboard` + `filesystem` | `format: image` 会读磁盘上的图片                   |
| `capture.ocr`        | `capture`    | `filesystem`               | 只 OCR 调用方给的文件，**不碰屏幕**                |
| `capture.find`       | `capture`    | `filesystem`               | 读两个图片文件做匹配，同样不碰屏幕                 |
| `capture.crop`       | `filesystem` | `filesystem`               | 纯文件裁剪；本次迁移中一度被加上 `capture`，已去掉 |

`capture.screenshot` 与 `clipboard.set` 是**收紧**：此前只声明 `capture: true`（或 `clipboard: true`）的指令就能写文件、或读任意路径。`capture.ocr` / `capture.find` 从「要求 `capture`」改成「要求 `filesystem`」，用它们的指令需要把 `permissions:` 里的 `capture: true` 换成 `filesystem: true`。`capture.crop` 无净变化。仓库里的示例已按最低要求改正（`capture.find` / `capture.ocr` 只留 `filesystem`）。

同时修掉一个更严重的问题：`clipboard.set` 的 `format: image` 原先**完全不做路径约束**——它是唯一一处绕过 `filesystem_roots` 的文件读取（`execute` 连 `ctx` 都没接）。现在与其它读取路径的动作一样走 `confine_path`。

### 权限门控新增快照测试

`crates/registry/tests/gate.rs` 把**迁移前**的门控固化成一张快照表，逐条断言 72 个已注册动作的声明与之一致，并保证没有任何已注册动作游离在快照之外。与旧表有意不同的 5 条（上表）由 `DIFFERENCES` 这张 `const` 表显式列出——**新增和删除类别都必须写在那里**，任何后续改动都得以一次可见的编辑呈现，而不是静默漂移。

### Directive schema 改为由类型生成

`schemas/directive.schema.json` 此前是**手写**的，且严重不完整：`steps` 只有 `{"type":"array"}`（**没有任何 item schema**）、`inputs`/`variables`/`permissions` 只有 `{"type":"object"}`、`on_error` 只是 `{"type":"string"}`。也就是说**编辑器根本校验不了指令主体**。

现在它由 `corex-engine` 的类型生成（可选特性 `schema`），schema 因此不可能描述解析器拒绝的形状：

| 位置          | 之前                | 现在                                                                                                         |
| ------------- | ------------------- | ------------------------------------------------------------------------------------------------------------ |
| `steps[]`     | 无 item schema      | `$ref: #/$defs/Step`（`anyOf` ActionStep / IfStep / RepeatStep / ParallelStep；`Trigger` 用的是 `oneOf`）    |
| `inputs[]`    | 无 item schema      | `$ref: #/$defs/InputDecl`                                                                                    |
| `permissions` | `{"type":"object"}` | `$ref: #/$defs/Permissions`，含完整默认值                                                                    |
| `on_error`    | `{"type":"string"}` | `$ref: #/$defs/OnError`（`enum`）                                                                            |
| `triggers[]`  | 手写                | **不变**（`const: cron/watch`、`additionalProperties: false`、`minItems`、`minimum`、`events` 枚举全部保留） |

两处刻意的调整：

- `steps` 不再有 `minItems: 1`。引擎本来就接受 `steps: []`（空 pipeline 是空操作），旧约束是一条**过严的幻影约束**。
- **`$schema` 从 draft-07 升到 2020-12**（生成器用 schemars 1.2.2），子 schema 引用因此由 `#/definitions/X` 变为 `#/$defs/X`。现代编辑器（VS Code 等）两者都支持，但**若你的工具链钉死了 draft-07 或 `definitions`，需相应调整**。

`$id` / `title` / `description` 保持不变。

嵌入方若启用 `schema` 特性，会多出 schemars（1.2.2）依赖；默认构建不受影响。

门禁：CI 运行 `cargo test -p corex-engine --features schema --test directive_schema`，签入文件与代码不一致即失败。重新生成：

```text
COREX_BLESS_SCHEMA=1 cargo test -p corex-engine --features schema --test directive_schema
```

### 模块归位：`ui_kernel` → `ui::kernel`

`corex_registry::builtin::ui_kernel` 是**公开可达**的模块，却与它所属的 `ui/` 目录平级：文件位置与职责不符（该文件只在 `ui` facade 与 Windows 适配器之间共享选择器/等待原语）。现已移入 `ui/kernel.rs`：

| 之前                                    | 现在                                     |
| --------------------------------------- | ---------------------------------------- |
| `corex_registry::builtin::ui_kernel::*` | `corex_registry::builtin::ui::kernel::*` |

顺带好处：它不再需要单独写 `#[cfg(feature = "act-ui")]`——`ui` 模块本身已是该门控。

`bins/cli` 的 clap 接口定义也从 `main.rs` 抽到 `cli.rs`，watch/cron 共用的作业逻辑从 `trigger_cmd.rs` 拆到 `scheduler/{mod,start,control,logs}.rs`；`main.rs` 里两份与它 **语义相同、仅写法不同**的指令路径解析改为直接复用后者（现为 `Paths::resolve` / `Paths::dir`），删掉重复实现。文件名也统一去掉了冗余的 `_cmd` 后缀（`watch_cmd.rs` → `watch.rs` 等），冗长的测试名同理（`example_directives_validate.rs` → `examples.rs`、`permissions_and_timeout.rs` → `limits.rs`）。

下表的「之前」是**本次重构动手前的工作区状态**（含本轮较早的几步改动），不是 v6.0.1 的行数：`crates/updater` 这个 crate 本身从未提交过——它在本次会话里先写成一个 603 行的 `lib.rs`，随后才拆开。

| 之前                               | 现在                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------- |
| `main.rs` 579 行                   | `main.rs` 454 行（+ `cli.rs`）                                            |
| `trigger_cmd.rs` 501 行            | `scheduler/mod.rs` 99 + `start.rs` 230 + `control.rs` 109 + `logs.rs` 124 |
| `crates/updater/src/lib.rs` 603 行 | `lib.rs` 260 + `plan.rs` 185 + `digest.rs` 91 + `stage.rs` 62             |

这些都是二进制或私有模块的内部结构，公共路径不变（`corex_updater::Plan` 等仍从 crate 根再导出）。模块内定义的名字也不再重复模块名——`check` 的 `CheckState` / `run_background_check` → `State` / `run_background`、`asset` 的 `AssetKind` / `SUMS_ASSET` → `Kind` / `SUMS`、`github` 的 `GithubClient` → `Client`、`stage` 的 `stage_binary` → `binary`、`proxy` 的 `system_proxy` / `platform_proxy` → `system` / `platform`——跨模块引用靠模块路径（`check::State`）消歧。

顺带删掉 `tests/e2e/smoke.rs`：它只有两行注释（`// Placeholder: …`），没有任何测试函数，也没被任何 Cargo target 或 workflow 引用——真正的端到端冒烟在 `crates/engine/tests/pipeline_smoke.rs`。空目录不进入版本控制。

### 命名与文案统一

标识符不再使用 `list` / `apply` / `load` 这类机械动词，注释与用户可见文案统一用中文。**action id（`ui.element.list`、`process.list`）、IPC 方法名（`list_directives`）与配置键（`use_system_proxy`）都是对外契约，一律不变。**

同轮修掉一个退出码问题：`corex ui …` 探测被权限门禁拒绝时，`run_probe` 用 `anyhow!("{e}")` 把 `ActionError` 的类型擦掉了，于是退出码报 1（失败）而不是 3（拒绝）——这与 `exit.rs` 表的设计相反。现在保留类型，拒绝即 3。

### 发布包不再包含 `pdfium.dll`

`pdfium/` 只是个**构建助手**（把 bundled DLL 拷到产物旁），但驱动它的东西并不存在：

- **没有任何 crate 依赖 `pdfium-render`**；Windows 发布目标的依赖图里也**没有 `libloading`**（Linux 侧经 `screenshots → … → libloading` 会拉到它，但不在发布产物上），全仓更没有 `#[link]` / `extern "C"`
  —— 也就是说**没有任何机制能加载那个 DLL**；
- `morph.meta` 与 `morph.render` 是**无条件失败的占位实现**（返回硬编码文案，不会去探测文件），与 DLL 在不在无关；
- 基于 `lopdf` 的动作（`morph.export` / `merge` / `split`）在 DLL **不可寻址**时照样正常执行（实测 `ok=true`）；
- 却因为 `pdfium` 是 workspace 成员，**全新克隆或 CI** 构建时会联网下载这个 7.2 MB 的原生库（DLL 被 gitignore），
  下载失败即构建失败，发布 ZIP 也会带上它。

现已把 `pdfium` 从 workspace 成员中摘出，并在两个 CI workflow 里移除下载与打包步骤。`pdfium/`、`assets/pdfium/`、`scripts/download-pdfium.ps1` 仍在仓库里但**不再参与构建**；将来实现这两个动作时，把 `"pdfium"` 加回 `members` 并引入 `pdfium-render` 即可（`Cargo.toml` 有注释）。

**影响**：ZIP 内容变为 `corex.exe` + `corex-daemon.exe`；`morph.meta` / `morph.render` 依旧报错（文档已改为标注「未实现」）；构建不再需要下载原生库（含全新克隆与 CI）。

### 体积与冷启动进入自动门禁

体积和启动耗时最容易靠「顺手加一个依赖」退化，且**没有任何现有闸门会变红**（测试全绿、clippy 全绿）。现在 CI 的 `build-and-test` 任务在构建后多一步「Cold start and binary size」：跑 10 次 `corex.exe --version` 取**上中位数**（排序后取第 6 个，样本数为 10），超过 2000 ms 即失败，并打印两个 exe 的体积。

上限刻意放宽：release 基线比它低约两个数量级，所以它抓的是**结构性回归**（启动时扫描插件目录、把运行时拉进启动路径），而不是时序噪声。实测值与本地复测方法见 [`docs/ops/性能基线.md`](../ops/性能基线.md)。

没有引入 `criterion` / 基准测试框架：那会给一个刚瘦身（摘掉 wasmtime、pdfium）的仓库重新加一棵基准依赖树，而当前**并没有已知的性能问题需要微基准去定位**；真正缺的是「不许悄悄退化」的守门人，由上面这一步承担。
