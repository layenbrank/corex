# 运行时配置

Corex 从 **`<数据目录>/config/corex.toml`**、**`<数据目录>/config.toml`** 或仓库 **`config/corex.toml`** 加载配置。CLI 与 Daemon 共用同一套逻辑。

数据目录优先级：

| 优先级    | 路径                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------- |
| 1（优先） | 环境变量 **`COREX_DATA_DIR`**（宿主与测试用它钉住目录）                                                   |
| 2         | 运行中二进制所在目录（`corex.exe` 旁，可写时）                                                            |
| 3         | Windows `%APPDATA%\corex\data`；Linux `~/.local/share/corex`；macOS `~/Library/Application Support/corex` |
| 4         | 当前目录 `.corex`                                                                                         |

路径 3 是 `directories` 的 `ProjectDirs`（限定符 `dev`、应用名 `corex`）给出的，**Windows 上带 `\data` 后缀**，
XDG 系不带。指令、token、历史、审计与端点记录（`endpoint.json`）都住在数据目录里，
所以随宿主分发 corex 时应显式设 `COREX_DATA_DIR`：否则“数据落在哪”会取决于 exe 在不在可写位置。

---

## 配置文件位置

按优先级（**找到即用**，不做合并）：

1. `--config <PATH>` 指定的文件（`corex` 与 `corex-daemon` 都支持）
2. `<数据目录>/config/corex.toml`
3. `<数据目录>/config.toml`（部署后常用）
4. 当前工作目录 `config/corex.toml`（开发时）

**文件存在但解析失败 → 命令直接失败（退出码 2），不会回落到默认值。** 这是刻意的：若静默回落，配置里 `strict_permissions = true` 旁边的一个拼写错误就会把安全开关无声关掉。

同理，**未知的 section 或键会被拒绝**——拼错的 `strict_permissons` 会报错，而不是被忽略。

升级配置后先自检：

```bash
corex validate                    # 不带路径时检查配置，报告生效的配置文件与其中的问题
corex validate path/to/foo.yaml    # 校验单个指令
```

`corex`、`corex-daemon` 与 `corex ui` 读的是**同一份**配置，不存在某个子命令看不见某个 section 的情况。

## 配置段说明

### `[daemon]` — IPC 服务

| 键            | 说明                                                                                        | 默认                                                                      |
| ------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `socket_path` | IPC 端点。Unix：socket 相对名或绝对路径；Windows：**只能是**命名管道（如 `\\.\pipe\corex`） | 省略 → 平台默认（Unix `<数据目录>/corex.sock`；Windows `\\.\pipe\corex`） |
| `lock_path`   | 单例锁文件                                                                                  | `corex.lock`                                                              |
| `token`       | IPC 鉴权密钥；空则读/写 `<数据目录>/token`                                                  | （自动生成）                                                              |
| `max_jobs`    | 同时**执行**的请求数上限：`1` 串行 / `> 1` 最多这么多 / `0` 不限                            | `4`                                                                       |

环境变量 **`COREX_TOKEN`** 优先于配置文件中的 `token`。

`max_jobs` 只限**执行类**请求（`run_directive` / `invoke`）；控制类（`ping` / `shutdown` /
`list_*`）不排队——它们是宿主判断「daemon 还活着吗」的手段。默认 `4` 是为了宿主的多任务并跑
（构建、拷贝、压缩之类互不相干的重活）；**要保住「两条指令不会同时驱鼠标键盘」这条 UI 自动化
前提就显式写 `max_jobs = 1`**。排队的请求每两秒收到一帧心跳，宿主据此把「在等」与「死了」
分开（见 [IPC 协议](../reference/IPC协议.md#进度帧-stream-true)）。

连接本身总是并发的，**同一条连接上的多条请求也各自推进**：一条慢请求不会让别的客户端、
也不会让同一个客户端上的探活 / 拉目录排到它后面（帧按 `id` 归位）。

⚠️ **Windows 上默认端点不随数据目录变化**：不写 `socket_path` 就恒为 `\\.\pipe\corex`，
而单例锁是**每个数据目录一份**。于是两个各带一份 `COREX_DATA_DIR` 的宿主会拄同一个管道名，
后起的那个 daemon 会因管道被占而启动失败（失败是响亮的：进程直接退出，也不会留下端点记录；
报错里会指向 `socket_path`）。
需要并存就**显式给每个宿主一个 `socket_path`**（如 `[daemon] socket_path = '\\.\pipe\my-app-corex'`）；
Unix 上则不必：默认端点是 `<数据目录>/corex.sock`，数据目录不同就天然隔离。

### `[plugins]` — 插件

| 键                 | 说明                                    |
| ------------------ | --------------------------------------- |
| `plugin_dir`       | WASM 插件目录（相对数据目录或绝对路径） |
| `disabled`         | 禁用的插件 ID 列表                      |
| `disabled_actions` | 禁用的 Action ID 列表（如 `shell.run`） |

### `[history]` — 执行历史

| 键        | 说明                       |
| --------- | -------------------------- |
| `enabled` | 是否写入 JSONL 历史        |
| `file`    | 历史文件名（相对数据目录） |

### `[logging]`

| 键      | 说明                                          |
| ------- | --------------------------------------------- |
| `level` | `trace` / `debug` / `info` / `warn` / `error` |
| `json`  | 结构化 JSON 日志（便于 SIEM）                 |

**这一节管的是守护进程。** 守护进程的日志流就是它的输出，所以 `level` 直接决定
`daemon.log` 的详细程度。

CLI 不受它控制：CLI 有专门的进度通道（stderr 上的 `✓ 动作  步骤  耗时` 行）与结果通道
（stdout），而不是日志流。两边的默认因此不同：

| 想看的       | 命令行                                         |
| ------------ | ---------------------------------------------- |
| 进度（默认） | 直接 `corex run <名称>`                        |
| 关掉进度     | `corex run <名称> --quiet`                     |
| 引擎日志     | `corex -v run <名称>`（debug）/ `-vv`（trace） |
| 环境变量控制 | `COREX_LOG=corex_engine=debug`                 |

进度行写 stderr、结果写 stdout，所以 `corex run x | jq` 与 `corex run x --json-events`
都不会被进度污染。

### `[runtime]` — 引擎行为

| 键                   | 说明                                           | 默认     |
| -------------------- | ---------------------------------------------- | -------- |
| `max_parallel`       | `parallel` 块最大并发                          | 8        |
| `step_timeout`       | 单步超时（0=不限）                             | 0        |
| `strict_permissions` | 拒绝未声明 permissions 的指令                  | false    |
| `filesystem_roots`   | 文件类 Action 允许访问的根路径（空=不限制）    | []       |
| `ui_profile`         | UI 自动化预设：`baseline` / `fast` / `patient` | baseline |
| `ui_settle_limit`    | 单次指令 `ui.wait` 累计上限（fast 预设 2000）  | 0        |
| `ui_selector_depth`  | `selectors[]` 最大长度                         | 8        |
| `cron_timezone`      | cron 默认时区：`local` / `utc` / `±HH:MM`      | `local`  |

#### UI profile 对照

| Profile    | `ui_selector_depth` | `ui_settle_limit` |
| ---------- | ------------------- | ----------------- |
| `baseline` | 8                   | 0（不限）         |
| `fast`     | 5                   | 2000              |
| `patient`  | 12                  | 0                 |

详见 [UI 自动化](../topics/UI自动化.md#runtime-ui-profile)。

### `[update]` — 自更新

| 键                     | 说明                                               | 默认                 |
| ---------------------- | -------------------------------------------------- | -------------------- |
| `enabled`              | 总开关；`false` 同时禁用 `corex update` 与后台检查 | true                 |
| `check_on_start`       | 启动时后台检查新版本（结果写 stderr）              | true                 |
| `check_interval`       | 两次检查的最小间隔（0=每次都查）                   | 24                   |
| `channel`              | `stable` / `alpha` / `beta` / `rc`                 | `stable`             |
| `repository`           | GitHub `owner/repo`，可指向内部镜像                | `layenbrank/corex`   |
| `api_base_url`         | 覆盖 API 根（GitHub Enterprise / 内网）            | 未设                 |
| `token_env`            | 存放 GitHub token 的环境变量名（`None`=不查找）    | `COREX_GITHUB_TOKEN` |
| `use_system_proxy`     | 无代理环境变量时回退到 Windows 系统代理            | true                 |
| `require_confirmation` | 替换前是否确认（`false` 等价于恒加 `--yes`）       | true                 |
| `timeout`              | 连接与单次读取超时（非整次传输上限）               | 30                   |

完整流程、校验链与故障排查见 [自更新](../reference/自更新.md)。

## 示例：企业收紧配置

```toml
[runtime]
strict_permissions = true
filesystem_roots = ["C:/ProgramData/MyApp/data"]

[plugins]
disabled_actions = ["shell.run", "ui.element.click"]

[logging]
json = true
level = "info"
```

## 审计日志

Daemon / CLI 执行时写入 `<数据目录>/audit.jsonl`（若可创建）。**每步一行** `AuditEntry`（JSON），
只追加。字段定义见 [`crates/engine/src/audit.rs`](../../crates/engine/src/audit.rs)。

成功一步（`error_kind` 为 `None` 时该键**不出现**）：

```json
{
  "name": "hello",
  "step_id": "greet",
  "action_id": "file.write",
  "duration_ms": 3,
  "ok": true,
  "denied": false
}
```

UI 步骤失败（选择器没等到）：

```json
{
  "name": "login-flow",
  "step_id": "wait-inbox",
  "action_id": "ui.element.wait",
  "duration_ms": 8002,
  "ok": false,
  "error_kind": "ui_sync_timeout",
  "denied": false,
  "ui_phase": "login",
  "error_code": "ui_sync_timeout",
  "selector_hint": "[role=button][name=收件箱]"
}
```

权限拒绝（`denied` 为 `true`，**不是**靠 `error_kind` 字符串判的）：

```json
{
  "name": "deploy",
  "step_id": "copy",
  "action_id": "file.copy",
  "duration_ms": 0,
  "ok": false,
  "error_kind": "permission_denied",
  "denied": true
}
```

| 字段            | 类型    | 何时出现                         | 说明                                                                                                      |
| --------------- | ------- | -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `name`          | string  | 总是                             | 指令名                                                                                                    |
| `step_id`       | string  | 总是                             | 步骤 id                                                                                                   |
| `action_id`     | string  | 总是                             | Action ID                                                                                                 |
| `duration_ms`   | number  | 总是                             | 该步骤耗时                                                                                                |
| `ok`            | bool    | 总是                             | 该步骤成败                                                                                                |
| `denied`        | bool    | **总是**（默认 `false`）         | `true` = 权限/策略拒绝                                                                                    |
| `error_kind`    | string? | 仅失败                           | 稳定分类，取自 `EngineError`/`ActionError::kind()`（见 [退出码与错误码](../reference/退出码与错误码.md)） |
| `ui_phase`      | string? | 仅 `ui.*` 与 `shell.run`         | `launch` / `login` / `act` / `verify`，由 Action ID 推断                                                  |
| `error_code`    | string? | 仅失败且消息带 `[ui_*]` 标签     | 如 `ui_login_pending`；无标签则无此键                                                                     |
| `selector_hint` | string? | 仅失败且带 `[selector_hint=...]` | **已脱敏**的选择器提示                                                                                    |

`ui_phase` 的推断规则（`infer_ui_phase`，只对 `ui.*` 与 `shell.run` 给出值）：
`shell.run` → `launch`；`ui.element.wait` → `login`；其它含 `element` → `act`；
`ui.window.*` → `verify`；其余 `ui.*` → `act`。

### 由 typed error 构造，不要手写

| 构造入口                       | 用于                                            |
| ------------------------------ | ----------------------------------------------- |
| `AuditEntry::from_engine(...)` | 流水线步骤（`EngineError`）                     |
| `AuditEntry::from_action(...)` | Daemon IPC `invoke` 与 UI 探测（`ActionError`） |

两个入口都会推导 `error_kind` 与 `denied`。手写 `AuditEntry { .. }` 会**丢掉这两项推导**，
v6 起不再支持「先写结构再补字段」——沿用旧写法会让审计里出现 `denied: false` 的权限拒绝。

### 记录里**没有**什么

审计**不含**请求体、OCR 结果与剪贴板内容；`selector_hint` 也经过脱敏。截图与 OCR 的产物本身
不在审计里，只在指令自己写出的文件里。字段级清单见 [威胁模型](../ops/威胁模型.md)。

### 与 `history.jsonl` 的分工

| 文件            | 粒度     | 内容                                                      | 用途                       |
| --------------- | -------- | --------------------------------------------------------- | -------------------------- |
| `audit.jsonl`   | **每步** | 上面那张表（有 `denied` / `error_kind` / UI 细化码）      | 合规、SIEM、失败归因       |
| `history.jsonl` | 每条指令 | `directive` / 起止时间戳 / `ok` / `duration_ms` / `error` | `corex history` 列最近运行 |

`history.jsonl` 的 `error` 是**脱敏并截断**（200 字符）后的文本，只适合给人看；
要机器可读的失败原因读 `audit.jsonl` 的 `error_kind` / `error_code`。

企业部署与 SIEM 取数见 [企业部署](../ops/企业部署.md) 与 [合规说明](../ops/合规说明.md)。
